# Line Launcher: архитектурный разбор и первый вертикальный срез

Студия **Plus In Plus**. Готовое брендируемое решение для провайдеров игровых серверов на основе Obsy Launcher. Оригинальные материалы Line — source-available (`LICENSE`), не полностью open-source; upstream Obsy остаётся MIT (`LICENSES/Obsy-MIT.txt`). Уведомления — `NOTICE.md`.

## 1. Четыре архитектурных решения

### 1.1. Сессия не должна путешествовать через JVM `-D`

Долгоживущий токен в аргументах процесса может оказаться в диагностике, списках процессов и crash reports. Случайный localhost-порт не является границей безопасности: к нему могут обращаться другие приложения пользователя. Передача секрета через stdin также требует отдельного анализа окружения и наследования дескрипторов.

Целевой контракт:

1. Rust авторизуется у провайдера **один раз на весь проект**; WebView получает только имя игрока и срок сессии. Сессия одна (`Option<ProviderSession>`), а не по серверу: вход открывает все серверы конфига, выход закрывает их все.
2. Перед запуском провайдер выдаёт одноразовый launch ticket с коротким TTL, привязанный к аккаунту, серверу и клиенту. Сервер запрещает повторный обмен.
3. Мод получает ticket через named pipe Windows с ACL текущего пользователя или Unix socket в каталоге `0700` / socket `0600`. JVM передаётся только несекретный rendezvous ID. Проверяются peer credentials там, где это поддерживает ОС.
4. Мод меняет ticket на игровую сессию и закрывает канал. Долгоживущий refresh/access token не покидает backend лаунчера.
5. Временный файл допустим как переходный вариант для **одноразового ticket**, с ограниченными правами, TTL и атомарным claim/delete. Он не защищает от вредоносного процесса того же пользователя. Шифрование полезно только при отдельном хранении ключа; ключ рядом с ciphertext не решает задачу.

**Статус кода:** токен хранится в Rust (`Zeroizing`), не сериализуется в WebView IPC. `launch.rs` запрашивает одноразовый ticket, создаёт приватный канал до spawn, проверяет peer-процесс, строит Java-аргументы с `sessionChannel` и запускает процесс. Справочный Java-клиент использует строгий JSON codec, HTTPS без redirect, таймауты и лимиты; `npm run test:java` проверяет обмен, replay/expiry/bindings и повреждённый IPC против локального provider stub. Exchange endpoint и mod-loader интеграция остаются ответственностью провайдера. Небезопасного `-DlineLauncher.sessionToken` fallback нет. Явный offline-режим сборки провайдера реализован без ticket/IPC; реальный запуск Minecraft с полным клиентом и production server-side одноразовость ticket ещё не проверены в этой среде.

### 1.2. ZIP: проверять до распаковки, публиковать после проверки

Обязательные поля: `sha256`, `size_bytes`, `unpacked_size_bytes`. Ссылка должна указывать на неизменяемый архив; изменение сборки требует нового URL/версии/хеша.

Реализованный pipeline:

```text
HTTPS chunks → archive.zip.part → exact size + SHA-256
  → bounded ZIP inspection → spawn_blocking extraction into staging
  → completion marker → immutable releases/<sha256>
  → atomic current.json publication
```

- Сеть асинхронная; распаковка и fsync выполняются в blocking pool.
- События ограничены примерно 80 мс; CSS Base UI сглаживает прогресс. При сетевом retry байты относятся к новой попытке, общий процент не откатывается назад.
- До трёх полных попыток для временных сетевых ошибок. Повреждение хеша не «лечится» бесконечным retry.
- `Range` намеренно не используется. Будущее resume требует сильного ETag, `If-Range`, проверки длины и полного итогового хеша. Слабый ETag/Last-Modified недостаточны.
- Zip Slip, абсолютные пути, `..`, backslash, ADS, device names, symlinks, специальные файлы, повторяющиеся пути и неизвестные методы сжатия отклоняются. Поддерживаются Stored/Deflate; лимиты 50 000 записей, 4 ГиБ ZIP, 16 ГиБ распаковки.
- Проверяются фактические размеры и CRC чтения ZIP, а не только заголовки. Проверяется свободное место с запасом на старую копию.
- Стадии не перезаписывают рабочий релиз. Ошибка удаляет staging; неудачная публикация оставляет прежний `current.json`. Immutable releases позволяют откатить указатель без обратной распаковки.
- Межпроцессный lock и очистка оставшегося staging после сбоя реализованы. Полная гарантия durability после отключения питания зависит от ФС; directory fsync выполняется на Unix.

Хеш обеспечивает целостность, но не доверие к автору. HTTPS и контроль конфигурации остаются ответственностью провайдера. Подпись самого config.json — следующий уровень защиты цепочки поставок.

### 1.3. Версии: формат отдельно от минимальной версии приложения

`schema_version: 1` определяет формат. `min_launcher_version` сравнивается через SemVer, включая prerelease precedence. Неизвестные необязательные поля допустимы. Неизвестный `required_features` или новая схема приводят к явной ошибке обновления, а не к попытке угадать формат.

TTL кэша ограничен 60–86400 секундами; отсутствие поля означает 300. Слишком новое требование никогда не обходится старым кэшем.

### 1.4. Кэш: быстрый просмотр, но не разрешение на запуск

Кэш атомарно сохраняется в per-user app data, проходит ту же валидацию, что сетевой документ. Поддерживаются ETag/304. Транспортная ошибка или временная ошибка сервера позволяет показать прежнюю конфигурацию с отметкой stale. 404/410, ошибка схемы, версии или данных не маскируются кэшем.

Новый интерфейс блокирует вход/установку по stale-конфигу. Токены и пароли в кэш не попадают. Автоматический offline-launch не предусмотрен.

## 2. Границы доверия и контракты

- JSON не может задать путь установки, Java executable или произвольные JVM-флаги.
- Tauri-команда установки принимает `serverId` и UUID операции; URL/хеш/назначение берутся из активного проверенного конфига.
- Только HTTPS, без URL credentials; redirects проверяются на каждом hop. Auth POST не следует redirects и не пересылает пароль другому origin.
- Конфиг и auth-ответы читаются с лимитом размера. Ошибки наружу имеют стабильный код, а не сырой текст HTTP-библиотеки/ответа.
- Пароли не пишутся в localStorage, логи или события. Ответы провайдера не логгируются. Zeroize уменьшает время жизни секретов, но не является защитой от скомпрометированной ОС.
- Конфигурация задаёт только данные витрины, auth endpoints, оформление серверов и дистрибутив. Запуск использует строгий `line-launch.json` внутри проверенного релиза: classpath/main class/JRE major, без произвольных JVM-флагов и путей.
- Настройки игрока ограничены по построению: heap в пределах безопасного лимита (не более 3/4 физической памяти и не более 16 ГиБ, минимум 1 ГиБ, значение вне диапазона отклоняется, а не подгоняется), выбор среди Java runtime, найденных самим лаунчером, размер окна, поведение после запуска и очистка кэша конфига. Свободного поля JVM-аргументов нет. Сохранённый путь к Java — только подсказка: он канонизируется и обязан присутствовать в результатах поиска и совпадать по major с manifest, иначе используется обычный поиск.
- **Гардероб локальный по умолчанию.** История скинов лежит в app-data (`skins/index.json` + `skins/<sha256>.png`) и работает без входа, без сети и у серверов вообще без skin API. Идентификатор — SHA-256 содержимого, поэтому одинаковые текстуры не дублируются, а `id` проверяется до построения любого пути (никаких `../`). Лимит 64 текстуры: при переполнении добавление отклоняется с понятным сообщением, а история не удаляется молча. Повреждённый или слишком большой индекс откатывается к пустому, но не ломает экран.
- **На сервер уходит только активный скин, автоматически.** Индекс хранит `active` и `synced` — одна пара на аккаунт, а не карта по серверам. Выбор активного (`set_active_skin`) остаётся чисто локальным: ни сессии, ни сети. Отправкой занимается `sync_active_skin`, которую интерфейс вызывает сам при монтировании гардероба, входе и смене активного скина: `sync_action` сравнивает `active` и `synced` и решает `Unchanged` / `Reset` / `Upload`. Ровно одна запись уходит в общий `wardrobe::push_skin`, отсутствие активного — `DELETE`. Кнопки «Отправить на сервер» и команд `upload_skin`/`reset_skin` в IPC больше нет.
- **Синхронизация идемпотентна и самовосстанавливается.** Отметка `synced` пишется только после успешного ответа провайдера, поэтому неудачная отправка повторяется при следующем входе или открытии гардероба, а неизменившийся скин не отправляется вовсе. Весь цикл (план → запрос → отметка) защищён `skin_sync: tokio::sync::Mutex<()>`, иначе параллельные вызовы могли бы записать отметку о текстуре, которой на аккаунте уже нет. `forget_synced_skin` сбрасывает отметку при входе и выходе, чтобы другой игрок не унаследил чужую. Результат `unchanged` не несёт скин — интерфейс не должен затирать им известное состояние.
- Отправка использует endpoints проекта (`provider.wardrobe.skin_url` / `skin_upload_url`) под bearer-сессией единого аккаунта. PNG проверяется трижды — в WebView, в Rust при добавлении в историю и повторно при отправке: ≤256 КиБ, 64×64 или 64×32, глубина 8, цвет 2/6, без interlace. Ответ ограничен 16 КиБ, `texture_url` обязан быть HTTPS.
- Серверный API и мод аутентификации — ответственность провайдера, как оговорено в постановке.

## 3. Roadmap и фактически выполненные изменения

### Выполнено в этом срезе

- Новый пакет/идентификатор/бренд Line Launcher, версия `0.1.0`.
- Удалены активные и исходные пути MSA/offline, ручных версий/загрузчиков, инстансов, аддонов, Modrinth/CurseForge/Discord RPC и произвольных JVM-флагов. Гардероб и ограниченные настройки игрока позже возвращены в безопасном виде (см. ниже).
- Удалены связанные Tauri-модули, разрешения и зависимости; сохранены общие Obsy/Base UI-примитивы.
- Удалён чужой updater endpoint/public key и автоматическая установка обновлений Obsy. Release workflow теперь строит неподписанные кандидаты без публикации.
- `src/types/line.ts`: публичный контракт конфигурации, IPC DTO и ошибки.
- `src-tauri/src/line/`: config/cache/auth/state/storage/http/install/launch/error-модули.
- `src/components/line/`: `ConfigUrlInput`, `ServerList`, `ServerCard`, `AuthForm`, `WelcomeScreen`, `SignInScreen`, `Skeleton` (заглушки загрузки по форме экранов), orchestration `LineLauncher`. Переводы — `src/lib/line/languages.ts` + `i18n-dictionaries.ts` + `i18n-core.ts` (стор) и `i18n.ts` (`useT`).
- `Button`, `Input`, `Label`, `Tabs`, `Progress` переиспользуются. Отдельных Card/Modal/ProgressBar в Obsy нет; карточки следуют `InstalledAddonCard`, диалоги — `Dialog`, прогресс — составному `Progress`.
- Tailwind v4, исходные токены и скругления Obsy без изменений, Framer Motion, Lucide, Base UI. Учтён reduced motion; карточки доступны с клавиатуры. Захардкоженные цвета убраны в пользу токенов Obsy.
- Build-time брендинг: `branding/line.brand.json` → генератор CSS/TS/Tauri-overlay/иконок, пресеты и переопределения только для семантических цветов, обязательная по лицензии видимая атрибуция Line Launcher | Plus In Plus (`docs/BRANDING.md`).
- Тесты контракта TS, тесты валидатора брендинга и Rust-тесты путей/размеров/symlink/cancellation/lock/atomic write/SemVer.
- CI переведён на npm lockfile: frontend/branding/license tests, Java-client integration matrix и Rust fmt/check/test/clippy на Linux/Windows/macOS. Rust-прогоны ещё должны быть выполнены в CI до релиза.

### Переводы и загрузка

- **Четыре языка, все в сборке.** `src/lib/line/languages.ts` — список (`ru`, `en`, `de`, `fr`), порядок и эндонимы для выбора; `i18n-dictionaries.ts` — каталог, где русский является источником истины, а `Dictionary` выводится из него, поэтому пропущенный ключ в любом языке — ошибка компиляции, а не строка, которая молча осталась русской. Все четыре словаря статически импортированы: переключение синхронное, без запроса и без промежуточного состояния. `i18n-core.ts` держит текущий язык как модульный стор (поэтому `t()` работает и вне React — в валидаторах скинов и ошибках IPC), `i18n.ts` добавляет `useT()` через `useSyncExternalStore`. Пока игрок не выбрал язык, `resolveLanguage` берёт язык системы, а русский остаётся языком по умолчанию; сохранённый выбор перебивает систему. Язык хранится в `LauncherSettings.language` вместе с остальными настройками (одна запись, одна схема, переживает переустановку WebView). `tests/i18n.test.ts` проверяет одинаковый набор ключей, отсутствие русского текста в латинских словарях, сохранность плейсхолдеров, порядок языков, названия всех двенадцати фонов и то, что выбор языка — первая секция настроек.
- **Skeleton-загрузка по форме элементов.** `src/components/line/Skeleton.tsx`: заглушки повторяют геометрию того, что заменяют, — карточка сервера (баннер 96 px, иконка 32 px, три строки текста), сетка каталога в тех же трёх колонках, страница сервера с доком, прижатым к нижнему краю, квадратный бокс 3D-просмотра в профиле, двухколоночный гардероб, строки истории сборок, карточка входа. Скелетоны `aria-hidden`, живые регионы вокруг них несут `role="status"`/`aria-busy`; при `prefers-reduced-motion` остаётся форма без мерцания. Спиннер остался только там, где скелетон невозможен: кнопки, которые уже нажаты, и повторная попытка после ошибки.

### Выполнено в срезе интерфейса игрока

- **Оболочка окна.** Собственный заголовок (`TitleBar`) вместо системного: `decorations: false`, drag-region, свернуть/развернуть/закрыть, состояние maximize отслеживается по событиям окна. Разрешения выданы точечно в `src-tauri/capabilities/default.json`. Генератор брендинга переносит в overlay **весь** объект окна: RFC 7386 заменяет массивы целиком, поэтому передача одного `title` теряла бы геометрию и возвращала системную рамку. Тест сверяет `BASE_WINDOW` с `tauri.conf.json`.
- **Провайдер всегда один и задаётся на сборке.** `branding/provider.json` → `src/brand/provider.generated.ts`: единственный `config_url`, вшитый в бандл. Лаунчер подключается к нему сам при запуске (`ConnectingScreen`), экрана ссылки и выбора провайдера нет. Серверы проекта приходят из этого конфига, а не из файла сборки. Пустой адрес — ненастроенный шаблон: поле ссылки доступно только под `npm run dev`, готовая сборка показывает «Сборка не настроена», а `tauri:build` останавливается. Кэш от постороннего адреса игнорируется; «Переподключиться» повторяет подключение к тому же адресу.
- **Боковая навигация** (`SideNav`): серверы / гардероб / настройки, сворачивается в полосу иконок, состояние сохраняется в настройках. Свёрнутый режим сохраняет `aria-label`, `aria-current` и атрибуцию по лицензии. Внизу панели показан логин и выход из аккаунта — он общий для всех серверов. Гардероб доступен всегда: история локальная, без сессии не происходит только автоматическая отправка.
- **Настройки** (`SettingsScreen`) переиспользуют `Select`, `Slider`, `Input`, `Button` из `src/components/ui/`. Сохранение атомарное (`settings.json` в app-data); повреждённый или слишком большой документ откатывается к значениям по умолчанию, чтобы не блокировать запуск.
- **Гардероб** (`WardrobeScreen` + `SkinPreview` + `SkinThumb`): выбор файла, проверка, предпросмотр передней проекции скина на canvas с `image-rendering: pixelated`, локальная история с выбором активного и удалением, автоматическая отправка активного скина со статусом вместо кнопки. Байты миниатюр приходят из Rust и превращаются в object URL в WebView — asset-протокол и `file://` не нужны, каждый URL отзывается при смене и размонтировании. Раскладка учитывает classic/slim и legacy 64×32 (зеркальные конечности, отсутствие второго слоя). Object URL отзывается, устаревшие ответы отбрасываются по счётчику поколений.
- **Оформление серверов.** `icon_url` и `banner_url` у каждого сервера: баннер в карточке списка и hero на экране сервера, отдельная иконка. `logo_url` у сервера читается как алиас `icon_url`. Недоступная картинка деградирует в заглушку, а не ломает раскладку.
- **Знак бренда** вынесен в отдельный прозрачный файл `branding/assets/logo.svg`. Знак с `currentColor` перекрашивается через CSS-маску в `--primary` и следует за пресетом; полноцветный выводится как есть.
- Оформление построено на семантических слотах (`bg-card/*`, `border-border/*`,
  `text-muted-foreground`), поэтому перекрашивается пресетом брендинга.
  Палитра, стеклянные поверхности и правила движения описаны в
  `docs/DESIGN.md`; тест проверяет отсутствие хардкод-цветов в компонентах.

### Исправления отзывчивости интерфейса

- **Стабильная геометрия форм.** Блок ошибки монтировался и размонтировался, меняя высоту карточки; так как карточка отцентрована, кнопка отправки подпрыгивала на 24px при каждом нажатии и возвращалась обратно. Теперь подсказка и ошибка занимают один слот с зарезервированной высотой (`aria-live="polite"`), поэтому кнопка неподвижна в состояниях покой/ошибка/загрузка. Самодельный `active:scale` убран: общий `Button` уже даёт отклик нажатием, а два трансформа конфликтовали.
- **Кастомная прокрутка.** Системная полоса заменена «пилюлей» на токенах Obsy (`docs/BRANDING.md`). Стандартные `scrollbar-width`/`scrollbar-color` применяются только в Firefox через `@supports`, иначе Chromium отключает `::-webkit-scrollbar` и пилюля не рисуется.
- **Недоступна только отправка, а не гардероб.** Объяснять причину блокировки оказалось недостаточно: проверить гардероб всё равно было нельзя. Раздел и пункт меню активны всегда; причина, по которой скин не уходит на сервер (нет входа / проект не настроил `provider.wardrobe` / ошибка отправки), показывается строкой состояния под «Скин на серверах проекта», а не заблокированной кнопкой.

### Единый аккаунт и автоматический гардероб

- **Один вход на проект.** Раньше форма входа появлялась на экране каждого сервера, а `selectServer` сбрасывал сессию — игроку приходилось логиниться заново. Теперь `AccountScreen` стоит между подключением и витриной: `provider.auth` принимает `{username, password}` без `server_id`, `LineState` хранит одну сессию, а `line_session` восстанавливает её при перезапуске. Открытие сервера, обновление конфига и переход между разделами вход не сбрасывают; сессия инвалидируется только при смене адреса, `provider.id` или `provider.auth`. Любая активная установка/запуск/откат на **любом** сервере блокирует смену аккаунта.
- **Схема без обратной совместимости.** `server.auth.login_url` и `server.wardrobe` удалены, а не поддержаны как алиасы: тихий откат к старому контракту вернул бы вход на каждом сервере. Валидатор отклоняет такой конфиг с явным сообщением, `examples/config.json` и `provider:pack` переведены на новую форму.
- **Гардероб без кнопки отправки.** Активный скин один на аккаунт и уходит сам. Состояния («отправляем» / «отправлен» / «не удалось, повторим») выводятся из результата команды, ошибки не блокируют локальную работу.
- **Истёкшая сессия возвращает ко входу.** `AUTH_REQUIRED` от установки, запуска или автоматической отправки скина сбрасывает сессию в интерфейсе и открывает экран входа с пояснением — мёртвой кнопки «Играть» не остаётся. Колбэк хранится в `ref`, а не в зависимостях `autoSync`: иначе inline-стрелка родителя меняла бы идентичность функции каждый рендер и эффект монтирования читал бы индекс в цикле.

> Светлая/тёмная тема **не** добавлена: палитра одна и она тёмная, а правило
> дизайна запрещает менять что-либо кроме семантических цветов. Второго дизайна
> тоже больше нет: раньше `data-theme="old"` открывал предыдущий интерфейс, но
> отката не случилось ни разу, а поддерживать две вёрстки, два листа стилей и
> сборочный флаг стоило дороже, чем они давали. Единственное оформление, которое
> меняется у игрока, — **фон** (`docs/DESIGN.md`). Пресеты брендинга при этом
> работают как раньше: пресет задаёт акцент, дизайн — форму и поверхности.

### Целостность сборки и каталог игрока

Каждый сервер имеет собственное дерево `instances/<id>/`: неизменяемый релиз
`releases/<sha256>` и отдельный записываемый `game/`, который и передаётся в
`--gameDir` вместе с рабочим каталогом процесса. Обновление и восстановление
сборки не затрагивают миры, настройки и скриншоты.

При распаковке считается sha256 каждого файла и публикуется `.line-files.json`
(до маркера `.line-complete`); архив с этими служебными именами отклоняется. Перед
запуском релиз сверяется с индексом под межпроцессной арендой: посторонние файлы
удаляются, изменённые/отсутствующие вызывают повторную загрузку проверенного
архива и повторную сверку, symlink или специальный файл — полное восстановление
без чтения по ссылке. Повторное расхождение сразу после восстановления
останавливает запуск с `INTEGRITY`. Решение «удалить или перекачать» — чистая
функция `integrity::compare`, покрытая тестами без файловой системы.

### Следующие этапы до production release

1. Provider exchange API и приватный IPC: **реализованы на стороне launcher** (`launch_ticket_url`, one-shot канал, PID/UID/ACL проверки). Справочный Java-клиент — `examples/mod-client/LineTicketClient.java`; интеграционный тест `npm run test:java` покрывает обмен/replay/expiry/bindings/redirect/oversize/malformed/timeout против локального stub. Интеграция с конкретным mod loader и production server-side хранение ticket остаются ответственностью провайдера.
2. Строгий `line-launch.json`, поиск/проверка JRE, classpath, spawn Java и контроль жизненного цикла игры: **реализованы**. Кнопка запуска появляется только при настроенных endpoints и установленном релизе. Добавлены аргументы реального клиента (`--uuid`, `--accessToken 0`, `--userType`, `--versionType`, `-Xss1M`, macOS `-XstartOnFirstThread`, `org.lwjgl.librarypath`, `log4j.configurationFile`) и allow-list игровых аргументов `game_args`; JVM-аргументы по-прежнему запрещены. Реальный Minecraft в этой среде не запускался, а мод-лоадеры с собственными JVM-флагами (Forge/NeoForge) текущим контрактом не покрыты — [GAME.md](GAME.md).
3. Явный rollback указателя, `history.json` и хранение текущего + двух последних релизов с защитой запущенного релиза: **реализованы**. Cross-process lease удерживается от чтения релиза до выхода Java; rollback резервирует состояние до blocking IO; повторная установка восстанавливает history/retention после сбоя. Ожидание lease при запуске отменяемо кнопкой «Отменить запуск».
4. Порядок событий игры: **реализован**. Каждый статус несёт монотонный `revision`; WebView отбрасывает устаревшие события, а `get_game_status` возвращает последний опубликованный переход, а не синтезированную фазу.
5. Windows ACL/macOS/Linux permission tests на реальных ОС, полное отключение питания, production HTTP integration tests, большие архивы и замер памяти/скорости. Lock recovery и crash staging cleanup покрыты Rust-тестами, но Rust compile/tests в этой среде ещё не выполнены.
6. Подпись кода, Line updater key/endpoint и политика распространения. Иконки и палитра теперь задаются через `branding/line.brand.json`; финальное утверждение бренда — за Plus In Plus.
7. Подписанный конфиг/manifest, pinned provider policy и согласованный API модерации/банов/скинов — только если это действительно нужно B2B-продукту.

## 4. Проверка

```sh
npm ci
npm test
npm run test:rust
npm run build
npm run test:java
npm run test:provider
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo test --locked --manifest-path src-tauri/Cargo.toml

npm run tauri dev
```

Frontend без Tauri показывает экран подключения, но сетевые/файловые операции требуют desktop shell. Никаких фиктивных успешных авторизаций или mock-download в рабочем интерфейсе нет.

Фактический статус проверок и ограничения песочницы зафиксированы в `docs/VERIFICATION.md`.
Полный Rust compile/tests/clippy, проверки на Windows/macOS, реальный Minecraft, подпись и
updater выполняются по пошаговой инструкции в `docs/RUNBOOK.md`; это не заявляется как
прошедшая проверка.
