# Промпт: аудит соответствия LineAuth спецификации лаунчера

Готовый промпт для ИИ-агента, который проверяет, что мод **LineAuth**
(Forge / Fabric / NeoForge) действительно работает с **Line Launcher** по
контракту [`SESSION-MODEL-A.md`](SESSION-MODEL-A.md).

Скопируйте блок ниже в агента, который имеет доступ к обоим репозиториям:
лаунчеру и моду. Замените `<путь-к-моду>` на реальный путь.

---

## Промпт

```text
Роль: аудитор интеграции. Ты проверяешь, что мод LineAuth действительно
совместим с Line Launcher по опубликованному контракту. Ты не переписываешь
код и не «улучшаешь» дизайн — ты находишь расхождения и доказываешь их.

## Что за система

Line DevKit — семейство продуктов Plus In Plus:
  • Line Launcher (этот репозиторий) — авторизует игрока и запускает игру;
  • LineAuth — мод на Forge / Fabric / NeoForge, который решает,
    пускать игрока на сервер или нет;
  • PIP ToolBox — появится позже.

Главный сценарий, который ОБЯЗАН работать:
  игрок вошёл в лаунчере под аккаунтом из БД провайдера → запустил игру →
  попал на сервер.
  игрок пришёл со сторонним лаунчером или аккаунтом, которого нет в БД
  провайдера → на сервер не попал, соединение отклонено с понятным текстом.

Мод не аутентифицирует сам: он получает готовую сессию от провайдера через
лаунчер и доказывает её серверу.

## Источники истины (в этом порядке)

1. `docs/SESSION-MODEL-A.md` — контракт сессии. Читай §0–§7 как требования,
   §12 как известные расхождения.
2. `docs/PROVIDER.md` — формат config.json и эндпоинты запуска.
3. `src-tauri/src/line/ipc.rs` — реальный формат приватного канала.
4. `src-tauri/src/line/launch.rs` — что попадает в аргументы JVM.
5. `examples/provider/server.mjs` — эталонный провайдер.
6. `examples/mod-client/LineTicketClient.java` — эталонный клиент.
7. `<путь-к-моду>` — проверяемый мод.

Правило: если документ и код расходятся — истина в коде лаунчера, а документ
считается дефектом. Каждое утверждение подкрепляй ссылкой `файл:строка`.

## Что проверить

### A. Получение сессии (блокер)

- [ ] Мод читает `-DlineLauncher.sessionChannel`. Нет свойства → понятное
      сообщение «Запустите игру через лаунчер проекта», без стектрейса и без
      падения игры.
- [ ] Путь к каналу совпадает с `ipc.rs` побайтно:
      Windows `\\.\pipe\line-launcher-<uuid>`,
      Unix `/tmp/line-ipc-<uuid>/ticket.sock`.
- [ ] Запрос — одна строка JSON `{"type":"line.launch-ticket.request","channel":"<uuid>"}`
      с `\n` в конце. Лишние поля ломают лаунчер: он использует
      `deny_unknown_fields`.
- [ ] Ответ читается с лимитом 16 КиБ и строгим набором полей:
      `type`, `ticket`, `exchange_url`, `server_id`, `sha256`, `username`.
      Набор полей должен совпадать ТОЧНО: и лишнее, и отсутствующее — ошибка.
- [ ] `type` равен `line.launch-ticket.response`.
- [ ] Таймаут IPC не больше 60 с и прерывается, если лаунчер молчит.

### B. Обмен ticket → сессия (блокер)

- [ ] Ровно один POST на `exchange_url`. Redirect запрещён
      (`Redirect.NEVER` или эквивалент). `exchange_url` обязан быть HTTPS;
      мод отвергает `http://`, встроенные логин/пароль и фрагмент.
- [ ] Тело — ровно пять полей: `ticket`, `server_id`, `sha256`,
      `channel_id`, `username`. `channel_id` — это uuid из свойства JVM,
      а НЕ что-то новое. Ни одно поле не придумывается.
- [ ] Таймауты: connect 10 с, запрос 30 с.
- [ ] Успех — только HTTP 200. Всё остальное — отказ.
- [ ] Тело ответа читается с лимитом 16 КиБ и **разбирается строго**:
      обязательные поля `session_id`, `session_secret`, `username`, `uuid`,
      `server_id`, `expires_in`; неизвестные поля — ошибка.
      → Известный дефект: `examples/mod-client/LineTicketClient.java` возвращает
        сырое тело и не разбирает его. Если мод скопирован оттуда — это блокер.
- [ ] `expires_in` — ЧИСЛО в диапазоне 30–600. Проверь, что JSON-парсер мода
      умеет числа: эталонный `LineJson` умеет только строки, и `expires_in: 120`
      у него падает. Это второй блокер рядом с первым.
- [ ] `server_id` в ответе совпадает с полученным по IPC; `username` тоже.
      Несовпадение — отказ, а не предупреждение.
- [ ] `uuid` — валидный UUID.
- [ ] `access_token` провайдера мод не получает и нигде не ищет.

### C. Хранение секрета

- [ ] `session_secret` и `session_id` живут только в памяти.
- [ ] Нет записи в файл, лог, чат, crash-report, аргументы JVM.
- [ ] `toString()/equals/hashCode` не печатают секрет (маскирование).
- [ ] Секрет не попадает в исключения: `IOException` с телом ответа — дефект.

### D. Доказательство серверу

- [ ] Мод принимает `nonce` от сервера в login-фазе (16+ случайных байт).
- [ ] Отвечает `proof = base64url(HMAC_SHA256(session_secret, nonce))`.
- [ ] `session_secret` НИКОГДА не уходит на игровой сервер — только `proof`.
- [ ] Отсутствие `nonce` — отказ, а не пустая строка в HMAC.
- [ ] Ответ серверу приходит за 10 с, иначе соединение не висит.

### E. Обработка отказов

- [ ] `409` → не повторять, сообщить «сессия уже использована, перезапустите
      игру из лаунчера».
- [ ] `401` → не повторять, «запустите игру заново из лаунчера».
- [ ] `403` → не повторять, «сборка не совпадает с опубликованной».
- [ ] `429` → не повторять в этом запуске.
- [ ] `5xx` и сетевой сбой ДО отправки ticket → допустим один повтор через 1–2 с.
- [ ] После окончательного отказа соединение завершается, а не висит.

### F. Соответствие модели угроз

- [ ] Мод не считает `--uuid` доказательством личности. UUID выводится из
      ника и проверяется локально кем угодно.
- [ ] Мод не пускает игрока при `online-mode=true` на сервере: лаунчер не
      подделывает сессию Mojang.
- [ ] Мод не обходит проверку, если `sessionChannel` есть, но канал не отвечает.

## Формат ответа

Сначала таблица, потом доказательства.

| # | Требование | Вердикт | Доказательство |
|---|-----------|---------|----------------|
| A1 | читает sessionChannel | OK / ДЕФЕКТ / Н/Д | `LineAuthAuth.java:88` |
| … | | | |

Вердикты:
  OK      — код делает именно это, ссылка на строку;
  ДЕФЕКТ  — код делает иначе: что именно, чем это грозит игроку, как починить;
  Н/Д     — проверить нельзя, укажи, что мешает.

Отдельным блоком:
1. Блокеры — без них главный сценарий не работает.
2. Расхождения с документом — где документ врёт, а где код.
3. Что документ не описывает, а мод уже решил сам (это надо внести в контракт).

Не выдумывай результаты: если строки нет — пиши «не найдено», а не «вероятно,
есть». Отсутствие `HMAC` в файле — это факт, который проверяется поиском, а не
догадка.

## Вне области проверки

- Дизайн UI лаунчера, скриншоты, темы фонов.
- Сборка установщиков и Rust-часть, кроме чтения `ipc.rs`/`launch.rs`.
- Выбор мод-лоадера и версии Minecraft.
- Продакшен-безопасность БД провайдера — только то, что видно в контракте.

## Критерий готовности

Мод совместим, если:
1. Все пункты A–E — OK.
2. Главный сценарий проверен хотя бы одним запуском: вход через лаунчер
   пускает, сторонний аккаунт — нет.
3. Ни один дефект не «известен и принят»: каждый либо исправлен, либо занесён
   в §12.2 спецификации с объяснением.
```

## Как этим пользоваться

1. Скопируйте промпт целиком. Он самодостаточен: агент не обязан знать
   историю проекта.
2. Дайте доступ к обоим репозиториям. Если агент видит только мод — он не сможет
   сверить пути канала и формат IPC, и половина проверок станет «Н/Д».
3. Прогоните **до** первого релиза мода и после каждого изменения в `ipc.rs`.
4. Результат «все OK» — не повод верить на слово: попросите приложить ссылки на
   строки и при повторной проверке сверьте их сами.

## Почему именно эти проверки

Каждый пункт закрывает дефект, который уже существует или который специально
сделан невозможным:

| Проверка | От чего защищает |
| --- | --- |
| Строгий разбор ответа обмена | Эталонный клиент возвращает сырое тело — мод без разбора «работает» на любом ответе |
| Числа в JSON-кодеке | `expires_in` в контракте — число, а эталонный парсер принимает только строки |
| `deny_unknown_fields` на лаунчере | Лишнее поле в запросе мода роняет канал: лаунчер отвечает ошибкой |
| Сверка `server_id` и `username` | Подмена ответа обмена иначе даёт игроку чужую личность |
| `channel_id` = uuid из JVM | Иначе привязка ticket к каналу не проверяется и канал можно переиспользовать |
| `proof` вместо секрета | Трафик `online-mode=false` не шифруется; голый `session_id` — предъявительский токен |
| Не считать `--uuid` аутентификацией | UUID выводится из ника локально кем угодно |
| Завершение после отказа | Мод, который «висит», держит игрока в чёрном экране без объяснения |
