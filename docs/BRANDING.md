# Брендинг Line Launcher

Line Launcher — готовое брендируемое решение для провайдеров игровых серверов.
Провайдер может переименовать лаунчер, поменять акценты, логотип в интерфейсе
и иконку приложения, не трогая код компонентов. Это source-available продукт
с обязательной атрибуцией, а не полностью open-source или безусловный
white-label fork.

**Брендинг применяется на этапе сборки (build-time).** Один файл →
генератор → готовое приложение. Никакой темы из сети, никакого runtime-переопределения
CSS из конфига провайдера.

## Главное правило дизайна

Line Launcher построен на UI/UX **Obsy Launcher**. Палитра, скругления, отступы,
компоненты и анимации унаследованы без изменений:

- `src/index.css` содержит исходные токены Obsy (`--primary: oklch(0.92 0.004 286.32)`,
  `--ring: oklch(0.92 0.004 286.32 / 45%)`, `--radius: 12px`).
- Пресет по умолчанию `obsy` **не создаёт ни одного переопределения** — сборка
  выглядит ровно как оригинал.
- Генератор умеет менять **только семантические цвета**. Попытка задать `radius`,
  `spacing`, `font` или любой неизвестный слот отклоняется с ошибкой.
- Компоненты `src/components/line/` переиспользуют `Button`, `Input`, `Label`,
  `Tabs`, `Progress`, `Dialog` из `src/components/ui/` и те же классы, что
  `StoreAddonCard`, `InstalledAddonCard`, `Onboarding`, `Header`, `LaunchButton`.

## Быстрый старт

```sh
# 1. Отредактируйте branding/line.brand.json (вид) и branding/provider.json (адрес)
# 2. Сгенерируйте файлы брендинга
npm run brand

# 3. Соберите брендированное приложение
npm run tauri:build
```

`npm run dev` и `npm run build` запускают `npm run brand` автоматически, поэтому
при обычной разработке ничего дополнительно делать не нужно.

## Файл `branding/provider.json` — адрес на этапе сборки

**Провайдер всегда один.** Владелец проекта собирает лаунчер под себя, поэтому
адрес его `config.json` задаётся один раз до сборки. Игрок ссылку не вводит: он
только регистрируется и входит.

```json
{
  "config_url": "https://example.com/line/config.json"
}
```

Список серверов здесь **не** перечисляется: сколько угодно серверов одного
проекта приходит из самого `config.json` (см. [PROVIDER.md](PROVIDER.md)).

| Поле         | Правило                                                             |
| ------------ | ------------------------------------------------------------------- |
| `config_url` | Только `https://`, без учётных данных и `#fragment`, ≤2048 символов |
| `$comment`   | Необязательный комментарий, игнорируется                            |

Любые другие ключи — ошибка сборки. В частности, старая форма со списком
`providers` отвергается с подсказкой: у сборки ровно один провайдер.

Поведение:

- **адрес заполнен** — лаунчер подключается сам при запуске, экрана ссылки нет
  ни в dev, ни в релизе; в меню вместо смены провайдера — «Переподключиться»;
- **адрес пуст** — это ненастроенный шаблон. Под `npm run dev` появится поле
  ссылки для разработки, а готовая сборка покажет «Сборка не настроена»;
- **сборка установщика** (`npm run tauri:build`) с пустым адресом **останавливается**:
  игроку не должно достаться приложение, к которому нельзя подключиться.

Адрес вшивается в бандл, поэтому проверяется на сборке теми же правилами, что и
ссылка, введённая в рантайме (`validate_https` в `src-tauri/src/line/config.rs`).
Это удобство, а не граница доверия: Rust перепроверяет URL перед каждым запросом.
Кэш конфигурации от другого адреса в настроенной сборке игнорируется.

## Файл `branding/owner.ts` — адрес издателя

Здесь лежит **только** адрес почты поддержки издателя: он попадает в кнопку
«Отправить в …» в настройках, рядом с «Скопировать диагностику».

```ts
export const OWNER = {
  support_email: "help@example.com", // null = кнопки письма не будет
  support_name: "Line Launcher",
};
```

Файл намеренно **вне** схемы брендинга. Провайдер перекрашивает сборку через
`line.brand.json` и `provider.json`; если бы адрес лежал там, перекрасивший
сборку мог бы перенаправить себе диагностику всех игроков. Ключ `owner` или
`support` внутри `line.brand.json` — ошибка сборки с объяснением, а не тихо
принятое значение.

Адрес провайдера задаётся отдельно, в его `config.json`
(`provider.support_email`), и открывает свою кнопку — «Связаться с
провайдером». Подробности: [LOGGING.md](LOGGING.md).

```json
    "short_name": "MyServer",
    "app_id": "com.example.launcher",
    "publisher": "My Studio",
    "window_title": "My Server",
    "description": "Официальный лаунчер моего сервера"
  },
  "assets": {
    "logo": "assets/my-logo.svg",
    "app_icon": "assets/my-icon.svg"
  },
  "attribution": {
    "placement": "footer",
    "language": "both"
  }
}
```

### Палитра не настраивается

Брендинг меняет **название, логотип и иконку**. Цвета — нет.

Раньше здесь были `preset` и `palette` с шестью готовыми палитрами. В 0.12.0
они удалены. Причина не в аккуратности, а в том, что интерфейс построен вокруг
этой конкретной палитры: глубокие поверхности, один яркий акцент, статусные
цвета подобраны под них. Подменённый акцент не «перекрашивает» лаунчер, а
ломает контраст, на котором держится читаемость панелей, и расходится с
градиентными фонами, которые сгенерированы под эти же оттенки.

Поэтому:

- конфиг со старыми `preset` или `palette` **не собирается**: `npm run brand`
  падает с текстом «the launcher palette is fixed»;
- `branding/presets.json` больше не существует; если файл остался от старой
  версии, генератор тоже откажется работать, пока его не удалят;
- `src/brand/generated.css` остаётся, но пустой — он ничего не переопределяет,
  а `src/index.css` с токенами Obsy остаётся единственным источником цветов.

Что это значит на практике: сменить «зелёный на фиолетовый» через брендинг
нельзя. Если палитра действительно мешает, это разговор про `docs/DESIGN.md` и
изменение дизайн-системы целиком, а не про одну строку в конфиге.

### `product`

| Поле           | Куда попадает                                                       |
| -------------- | ------------------------------------------------------------------- |
| `name`         | Заголовок в шапке, диалог «О программе», имя бандла (`productName`) |
| `short_name`   | Компактная подпись в футере                                         |
| `app_id`       | Bundle identifier. **Меняет каталог данных приложения** — см. ниже  |
| `publisher`    | Издатель в бандле и в «О программе»                                 |
| `window_title` | Заголовок окна ОС                                                   |
| `description`  | Описание бандла и текст в «О программе»                             |

> **`app_id` и данные пользователя.** Кэш конфигурации и установленные сборки
> живут в per-user app-data каталоге, который Tauri выводит из `app_id`. Смена
> идентификатора даёт приложению новый пустой каталог. Меняйте его один раз до
> первого релиза.

### `assets`

Пути относительны каталогу `branding/`, только `.svg` или `.png`, без `..`.

- `logo` — **отдельный файл знака без фона**, который показывается в заголовке
  окна и в боковой навигации. По умолчанию — `assets/logo.svg`, нейтральная
  прозрачная заглушка 32×32; замените её своим файлом и выполните `npm run brand`.
  `null` возвращает встроенный знак Lucide `Layers2`.

  Фон рисовать не нужно: знак кладётся на `bg-card`, плашку под ним рисует сам
  интерфейс по токенам Obsy. Квадратный `viewBox`, поля около 10% — иначе знак
  будет выглядеть мельче соседнего текста.

  **Как знак получает цвет.** Если в SVG есть `currentColor`, генератор помечает
  бренд флагом `logoTinted: true`, и `BrandMark` рисует знак через CSS-маску
  цветом `--primary`. Такой знак автоматически следует за любым пресетом палитры.
  Если в SVG заданы собственные цвета, он выводится как есть (`<img>`) и при смене
  палитры цвет не меняется — это осознанный выбор для полноцветного логотипа.
  Хотите перекрашиваемый знак — используйте `currentColor` и не задавайте `fill`
  цветом.
  Пути в `assets.*` задаются **относительно каталога `branding/`**: для файла
  `branding/assets/app-icon.svg` значение — `assets/app-icon.svg`, а не
  `branding/assets/app-icon.svg` (иначе путь двоится и генератор об этом скажет).

- `app_icon` — исходник иконки приложения, либо `null`, чтобы оставить уже
  сгенерированные иконки в `src-tauri/icons`. Если путь указан, файл обязан
  существовать: генератор сообщает, какой ключ конфигурации на него ссылается.
  Квадратный SVG или PNG, лучше
  1024×1024. Из него `tauri icon` генерирует `.ico`, `.icns` и весь набор PNG.

> **Иконка меняется не там, где логотип.** Логотип в шапке — обычный файл,
> который отдаёт интерфейс: он обновляется при следующей перезагрузке окна.
> Иконка приложения вшита в исполняемый файл (`.exe`, `.app`, установщик),
> поэтому её видно только в пересобранной программе:
>
> | Что запускали               | Что будет с иконкой                                 |
> | --------------------------- | --------------------------------------------------- |
> | `npm run demo`, `tauri dev` | Ничего: dev-режим не создаёт ярлыков и установщика. |
> | `npm run tauri:build`       | Пересоберёт иконки и вложит их в установщик.        |
> | Уже установленный лаунчер   | Остаётся старая, пока не поставить новую сборку.    |
>
> Отсюда «логотип сменился, а иконка нет»: интерфейс подхватил новый знак
> сразу, а ярлык принадлежит той сборке, которую когда-то установили.
> `npm run brand` пересоздаёт `src-tauri/icons`, но подменить иконку в уже
> установленном ярлыке он не может — это делает только установщик.
>
> `build.rs` следит за файлами в `icons/`, поэтому после пересборки иконок
> `cargo` перелинковывает бинарник и вкладывает новый значок. Без этого даже
> полная пересборка могла оставить старую иконку: скрипт сборки не знал, что
> иконки — его входные данные.

> В SVG-комментариях нельзя использовать `--`: парсер `tauri icon` на этом
> падает. Обычные XML-комментарии без двойного дефиса безопасны.

### Прокрутка и служебные элементы

Скроллбар — кастомная «пилюля» в `src/index.css`, а не системная полоса. Он
построен на семантических токенах, поэтому любой пресет перекрашивает его без
дополнительной настройки и без новых слотов палитры:

| Часть          | Токен                                                              |
| -------------- | ------------------------------------------------------------------ |
| Трек           | прозрачный (видна поверхность под ним)                             |
| Бегунок        | `--foreground` 22% → 34% при наведении на область → 48% на бегунке |
| Перетаскивание | `--primary` 70%                                                    |

Форма задаётся `border-radius` и прозрачной рамкой 2px с
`background-clip: content-box` — бегунок не касается содержимого. Ширина паза
10px, видимая пилюля 6px. При `prefers-reduced-motion` переход цвета отключается.

> **Не задавайте `scrollbar-width`/`scrollbar-color` без условия.** В Chromium
> (в том числе WebView2) эти свойства заставляют браузер полностью игнорировать
> `::-webkit-scrollbar`, и пилюля молча превращается обратно в системную полосу.
> В проекте они обёрнуты в `@supports not selector(::-webkit-scrollbar)` и
> применяются только в Firefox; тест это фиксирует.

### Цвета состояний

Успех, предупреждение и ошибка используют цвета Obsy (`emerald`, `amber`,
`destructive`) и намеренно не выведены в конфиг: они подобраны под фон и
проверены на контраст вместе с остальной палитрой. Единственный способ
изменить любой цвет интерфейса — правка `src/index.css` и обновление
`docs/DESIGN.md`, то есть изменение дизайн-системы, а не брендинг сборки.

### `attribution` — обязательное упоминание

Упоминание **Line Launcher | Plus In Plus** обязательно по [LICENSE](../LICENSE).
Это условие разрешения на использование и распространение материалов Line:
без упоминания права не предоставляются, а нарушение прекращает действие
разрешения. Конфиг выбирает только постоянное место и язык:

| `placement` | Где видно                                      |
| ----------- | ---------------------------------------------- |
| `footer`    | Постоянная строка в футере (по умолчанию)      |
| `header`    | Постоянная строка в шапке, без скрытия на `sm` |

| `language` | Текст                                                   |
| ---------- | ------------------------------------------------------- |
| `ru`       | Работает на Line Launcher \| Plus In Plus               |
| `en`       | Powered by Line Launcher \| Plus In Plus                |
| `both`     | Обе фразы через вертикальный разделитель (по умолчанию) |

Диалог «О программе» всегда повторяет упоминание **дополнительно**. Режим
`about` как единственное место больше не принимается: надпись должна быть
видна в основном интерфейсе при настройке, входе, выборе сервера и установке.
Кнопка About — иконка `Info` в шапке. Разделитель внутри фразы — `|`, не `·`.

Генератор падает с ошибкой, если:

- секция `attribution` отсутствует;
- добавлено любое поле кроме `placement` и `language` (`enabled`, `hidden`,
  `text` и т. п.);
- `placement` не `footer`/`header` или `language` не `ru`/`en`/`both`.

Сами фразы — константы в `branding/brand.types.ts`, а не данные конфига.
Оба названия и разделитель должны сохраняться; перевод или замена только
брендом провайдера не разрешены.

> **Граница защиты.** Валидатор защищает штатный путь сборки от случайного или
> явного отключения через конфиг. Это не DRM: исходники доступны, и намеренная
> правка генератора, компонента, CSS или бинарника технически возможна, но
> выходит за пределы лицензии и делает использование неразрешённым.
> Исходные материалы Obsy остаются MIT; новая лицензия применяется к
> оригинальным материалам Line и не отзывает upstream-права.

## Что генерируется

| Файл                              | Назначение                                                                     |
| --------------------------------- | ------------------------------------------------------------------------------ |
| `src/brand/generated.css`         | Только цветовые переопределения. Подключён в `src/index.tsx` после `index.css` |
| `src/brand/generated.ts`          | Типизированные константы продукта и атрибуции                                  |
| `src/brand/provider.generated.ts` | Вшитый адрес провайдера из `branding/provider.json`                            |
| `src/brand/logo.svg\|png`         | Копия знака; импортируется, чтобы Vite его хешировал                           |
| `src-tauri/tauri.brand.conf.json` | Overlay для `tauri build -c`                                                   |
| `src-tauri/icons/*`               | Иконки ОС и контрольные суммы исходника и созданных файлов                     |
| `src-tauri/LICENSE.rtf`           | Лицензия для MSI: ASCII с `\uN`-escape из `LICENSE` (RUNBOOK, 1.11)            |

Все файлы детерминированы и сохраняются в репозитории. Повторный запуск ничего не меняет.
Иконки пересоздаются при изменении SHA-256 исходника или если любой созданный файл отсутствует либо отличается от списка `src-tauri/icons/.brand-files.sha256.json`. `brand:check` сообщает о расхождении и сам файлы не меняет. Файлы внутри `icons/` генерируются, поэтому не редактируйте их вручную.

### Проверка значка внутри Windows exe

```powershell
npm run brand:check
npm run icon:check -- "D:\путь\к\line-launcher.exe"
```

Вторая команда сравнивает **первую группу значков внутри указанного exe** с текущим `src-tauri/icons/icon.ico`, включая все его размеры. `npm run demo:build` и Windows `npm run tauri:build` выполняют эту проверку автоматически. При несовпадении пересоберите приложение; команда не меняет старые установленные копии и ярлыки.

Если проверка совпала, а Проводник показывает другой значок, сначала убедитесь, что открыли именно проверенный путь, а не старую копию или ярлык. Проводник может показывать сохранённое изображение: обновите папку клавишей F5 или проверьте копию exe с другим именем. Проверка не анализирует иконку установщика или цель ярлыка и не очищает системный кэш.

## Команды

```sh
npm run brand         # применить брендинг
npm run brand:check   # проверить, что файлы актуальны (для CI)
npm run tauri:build   # brand + сборка установщиков (на Windows: NSIS, затем MSI)
```

`npm run brand -- --skip-icons` пропускает генерацию иконок, если нужен только
CSS/TS (например, в лёгком CI-джобе).

`LICENSE.rtf` править руками нельзя: он генерируется из `LICENSE`. MSI берёт его через
overlay `src-tauri/tauri.msi.conf.json`, NSIS — обычный `LICENSE`, потому что выводит
лицензию как простой текст.

## Почему иконка приложения меняется только при сборке

Иконка вшита в бандл (`.ico` в exe, `.icns` в `.app`, PNG в `.desktop`). Tauri
умеет менять иконку окна в runtime через `Window::set_icon`, но в `tao` это
no-op на macOS, а иконку в панели задач или Dock это не заменяет. Поэтому
единственный одинаковый для всех ОС способ — генерация на сборке, что и сделано.

## Проверка

`tests/brand.test.ts` покрывает: сохранение палитры Obsy по умолчанию, запрет
геометрии, обязательность атрибуции и точные фразы с `|`, запрет About-only и
произвольных полей атрибуции, приоритет override над пресетом, отклонение
CSS-инъекций и небезопасных путей, reverse-DNS `app_id`, детерминированность.
`tests/license.test.ts` проверяет лицензии, метаданные и включение правовых
текстов в ресурсы desktop-бандла.
