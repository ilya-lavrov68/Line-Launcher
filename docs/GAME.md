# Запуск реальной сборки и защита файлов

Документ о том, что лаунчер делает при нажатии «Играть»: как собирается команда
Java, где живут файлы каждого сервера и что происходит, если сборку изменили на
диске. Контракт провайдера — в [PROVIDER.md](PROVIDER.md), быстрый старт — в
[START.md](START.md), демо без своего сервера — в [DEMO.md](DEMO.md).

## 1. Один сервер — один экземпляр

Данные лежат в каталоге приложения (`%APPDATA%\studio.plusinplus.line-launcher`,
`~/Library/Application Support/studio.plusinplus.line-launcher`,
`~/.local/share/studio.plusinplus.line-launcher`):

```
instances/
  survival/
    releases/
      <sha256>/            ← распакованная сборка, только для чтения
        client.jar
        libraries/…
        assets/…
        natives/…
        line-launch.json
        .line-files.json   ← индекс: путь + sha256 + размер каждого файла
        .line-complete     ← маркер завершённой установки
    game/                  ← миры, options.txt, resourcepacks, логи игры
    logs/launch.log        ← stdout/stderr процесса Java
    current.json           ← указатель на активный релиз
    history.json           ← текущий + два предыдущих релиза
    .install.lock          ← межпроцессная аренда
  creative/
    …                      ← полностью отдельное дерево
```

Сборки двух серверов никогда не пересекаются: даже одинаковый релиз распаковывается
в каталог своего сервера. Каталоги `game/` тоже разные — миры, настройки и скриншоты
одного сервера не видны другому.

`--gameDir` и рабочий процесс Java указывают на `instances/<id>/game`, а **не** на
`releases/<sha>`. Поэтому:

- обновление сборки не удаляет миры и настройки;
- восстановление повреждённой сборки не трогает данные игрока;
- файлы внутри `releases/<sha>` остаются ровно теми, что опубликовал провайдер.

## 2. Офлайн-сборка провайдера

У сервера может быть явный `"launch_mode": "offline"` вместо пары
`launch_ticket_url` / `session_exchange_url`. Тогда лаунчер скачивает и проверяет
ваш ZIP, берёт ник из аккаунта проекта и запускает клиент **без ticket**, без
приватного IPC-канала и без ожидания мода авторизации. Microsoft-вход не нужен.
В `required_features` укажите `offline-launch-v1`.

Это не загрузчик пиратских копий: клиент, библиотеки, ассеты и нативы берётся из
ZIP, который разместил владелец проекта, а не с чужого зеркала. Сборка должна быть
полной и соответствовать манифесту; произвольный `client.jar` без зависимостей не
запустится. Защита файлов, отдельный каталог миров, выбор Java и остановка процесса
работают одинаково в обоих режимах. Просто отсутствующая авторизация не означает
offline: кнопка останется выключенной.

## 3. Команда запуска

Лаунчер собирает аргументы сам; произвольные JVM-флаги из конфига или манифеста не
принимаются. Пример для реальной сборки:

```
java -Xmx4096M -Xms4096M -Xss1M
     -XX:+UseG1GC … (набор G1-флагов)
     -DlineLauncher.sessionChannel=<uuid канала>
     -Djava.library.path=<release>/natives/linux
     -Dorg.lwjgl.librarypath=<release>/natives/linux
     -Dlog4j.configurationFile=<release>/log4j2.xml
     -cp <release>/client.jar:<release>/libraries/…
     net.minecraft.client.main.Main
     --gameDir <instance>/game
     --username Player_1
     --version 1.21.1
     --uuid <стабильный uuid аккаунта>
     --accessToken 0
     --userType mojang
     --versionType release
     --assetIndex 21 --assetsDir <release>/assets
     [--launchTarget forgeclient --fml.forgeVersion 47.2.0 …]
```

Что здесь важно:

| Аргумент                        | Откуда берётся                                    | Зачем                                                                        |
| ------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------- |
| `-Xss1M`                        | лаунчер                                           | без него генерация мира падает со `StackOverflowError`                       |
| `-XstartOnFirstThread`          | лаунчер, только macOS                             | требование LWJGL 3                                                           |
| `-DlineLauncher.sessionChannel` | только ticket-режим                               | в offline-режиме канал не создаётся и свойство не передаётся                 |
| `-Dorg.lwjgl.librarypath`       | `natives_dir` манифеста                           | LWJGL 3 не читает `java.library.path`                                        |
| `-Dlog4j.configurationFile`     | `logging_config` манифеста                        | штатные логи игры вместо предупреждений log4j                                |
| `--uuid`                        | sha256 от имени аккаунта провайдера               | один аккаунт → один uuid, миры сохраняют данные игрока                       |
| `--accessToken 0`               | константа-заглушка                                | настоящий ticket идёт только по приватному IPC и не виден в списке процессов |
| `--userType`                    | `user_type` манифеста (`mojang`, `msa`, `legacy`) | тип профиля для клиента                                                      |
| `--versionType release`         | лаунчер                                           | подпись версии в клиенте                                                     |
| `--gameDir`                     | `instances/<id>/game`                             | данные игрока отдельно от сборки                                             |

`--uuid` — идентификатор, а не средство авторизации: авторитетный профиль клиент
получает от `session_exchange_url` провайдера через одноразовый ticket
([PROVIDER.md](PROVIDER.md), раздел «Запуск игры»).

### Дополнительные аргументы сборки

Манифест может передать `game_args` — только парами `--имя значение`:

```json
"game_args": ["--launchTarget", "forgeclient", "--fml.forgeVersion", "47.2.0"]
```

Правила (проверяются и при установке, и перед spawn): не больше 128 аргументов,
имя из букв/цифр/`. _ -`, значение непустое, без управляющих символов и без
ведущего `-`. Запрещено переопределять `--gameDir`, `--username`, `--uuid`,
`--accessToken`, `--userType`, `--version`, `--versionType`, `--assetIndex`,
`--assetsDir`, `--session`, `--userproperties`, а также семейство `-X`/`-XX` и
модульные ключи JVM (`--add-opens`, `--patch-module`, `--class-path` и т. п.).
Дубликаты имён отклоняются.

## 3. Проверка файлов перед каждым запуском

Маркер `.line-complete` подтверждает только то, что распаковка дошла до конца.
Этого мало: jar можно подменить, библиотеку удалить, а рядом положить свой мод.
Поэтому при распаковке лаунчер считает sha256 **каждого** файла и пишет
`.line-files.json`:

```json
{
  "schema_version": 1,
  "files": [
    { "path": "client.jar", "sha256": "…64 hex…", "size": 12345678 },
    { "path": "libraries/core.jar", "sha256": "…", "size": 456 }
  ]
}
```

Индекс пишется **до** маркера, поэтому релиз не может считаться установленным без
списка файлов. Архив, внутри которого есть `.line-files.json` или `.line-complete`,
отклоняется целиком: провайдер не подделывает служебные файлы лаунчера.

Дальше при каждом запуске, под той же межпроцессной арендой, что и установка:

| Что нашлось                                 | Что делает лаунчер                                                                                    |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Всё совпало                                 | запускает игру                                                                                        |
| Посторонний файл (его нет в индексе)        | удаляет файл, подчищает опустевшие каталоги, пишет в статус «удалено посторонних — N», запускает игру |
| Файл изменён (тот же размер, другие байты)  | скачивает и распаковывает сборку заново, затем проверяет повторно                                     |
| Файла не хватает                            | то же: полное восстановление из проверенного архива                                                   |
| Индекса нет (ставила старая версия)         | восстановление заново                                                                                 |
| Вместо файла — symlink или специальный файл | ничего не читает по ссылке, восстанавливает релиз целиком                                             |
| После восстановления файлы снова изменены   | запуск не выполняется, ошибка `INTEGRITY` с текстом про диск/антивирус                                |

Восстановление скачивает ту сборку, которую провайдер объявляет актуальной сейчас:
если он успел выпустить новую версию, установится она, а не старая.

Восстановление — это обычный проверенный путь установки: скачивание,
сверка sha256 архива, безопасная распаковка в staging, публикация атомарной
заменой каталога релиза. Аренда на время скачивания отпускается (её берёт сам
установщик) и берётся снова для повторной проверки. Кнопка «Отменить запуск»
прерывает и восстановление. Прогресс восстановления идёт тем же событием
`line://install-progress`, а в статусе игры видно текст «Проверка файлов: сборка
изменена или неполная — скачиваем заново».

Проверка читает весь релиз целиком, поэтому на сборке в несколько гигов занимает
несколько секунд: под кнопкой видно «Проверка файлов сборки…», а сама кнопка
меняется на «Отменить запуск».

Проверка нарочно не пытается «починить» отдельный файл: единственный источник
правды — архив, чей sha256 объявлен в конфиге провайдера, полученном по
проверенному HTTPS.

## 4. Как провайдеру упаковать настоящий клиент

Лаунчер не скачивает Minecraft сам: ни клиентов, ни ассетов, ни библиотек со
сторонних зеркал. Провайдер сам собирает ZIP и сам отвечает за право его
распространять. Требования к содержимому:

1. **Полнота.** Всё, что нужно клиенту, лежит внутри архива: `client.jar`,
   `libraries/**`, `assets/**` (индексы и объекты), `natives/<os>/**`, конфиги
   модов. Докачки по `version_manifest.json` нет.
2. **Манифест.** `line-launch.json` в корне — см. [PROVIDER.md](PROVIDER.md).
   `java_major` должен точно совпадать с установленной у игрока Java.
3. **Нативные библиотеки.** Раскладывайте по каталогам ОС и указывайте нужный
   `natives_dir`; лаунчер подставит его в `java.library.path` и
   `org.lwjgl.librarypath`.
4. **Авторизация.** Аккаунты — свои, провайдерские. Мод/агент внутри сборки
   получает одноразовый ticket по приватному каналу, меняет его на игровую сессию
   через `session_exchange_url` и уже этой сессией заходит на сервер.
   Справочный клиент: `examples/mod-client/LineTicketClient.java`.
5. **Никаких секретов в аргументах.** `--accessToken 0` — заглушка; передавать
   токен через argv нельзя, его видит любой локальный процесс.

Проверить упаковку удобно на демо-провайдере: `npm run demo` поднимает три
сервера, каждый со своей сборкой, и показывает лог запуска
(`instances/<id>/logs/launch.log`).

## 5. Режим Minecraft через `mc-launcher-core`

Рядом с провайдерскими сборками есть отдельный режим: установка vanilla, Fabric,
Quilt, Forge и NeoForge с официальных площадок Mojang и запуск с автономным
аккаунтом. Провайдерские релизы он не трогает. Что работает с таким аккаунтом, а
что требует входа Microsoft, — в [MINECRAFT.md](MINECRAFT.md).

## 6. Чего нет в провайдерском ticket-запуске

Ограничения ниже относятся к пути с провайдерским `pack.json` и `game_args`,
а не к отдельному режиму `launch_mode: minecraft`. Его возможности и открытые
риски описаны в [MINECRAFT.md](MINECRAFT.md) и
[INSTALLATION-AUDIT.md](INSTALLATION-AUDIT.md).

- **Официальная авторизация Microsoft и проверка лицензии Minecraft не
  реализованы** и не планируются в этом контракте: лаунчер работает с аккаунтами
  провайдера. Право распространять клиент — на провайдере.
- **Мод авторизации** (ticket → сессия → join) пишет провайдер; в репозитории есть
  только справочный Java-клиент и контракт.
- **Forge/NeoForge целиком не запускаются**: им нужны собственные JVM-флаги
  (`-p`/`--add-modules`, `--add-opens`, `-DlegacyClassPath`), а манифест
  намеренно не принимает JVM-аргументы. `game_args` покрывает только игровые
  аргументы. Fabric-подобные сборки, которым хватает classpath и игровых
  аргументов, укладываются в текущий контракт.
- **Ассеты и нативы не докачиваются**: неполный пак не запустится, ошибка будет в
  логе игры.
- **Overlay пользовательских файлов** (свои mods/config по политике провайдера)
  не реализован: посторонние файлы в релизе удаляются, для своих сборок нужен
  отдельный механизм.
- **Провайдерский ticket-путь с настоящим Minecraft и модом не подтверждён**: он проверяется
  демо-клиентом (`examples/provider/DemoGame.java`) и тестами; полный
  `cargo test`/`clippy`, Windows-установщики и запуск настоящего клиента остаются
  за машиной с JDK, Rust и лицензией на распространение — см.
  [VERIFICATION.md](VERIFICATION.md).

## 7. Чем это проверяется

```sh
npm run test:rust     # чистая логика: сравнение индекса, удаление, argv, uuid
npm test              # контракт манифеста, типы, статические проверки wiring
npm run demo:check     # упаковка/раздача сборок локальным провайдером
cargo test --manifest-path src-tauri/Cargo.toml      # распаковка+индекс+скан на ФС
```

`npm run test:rust` гоняет реальные функции и их реальные unit-тесты без
crates.io: решение «что удалить/что перекачать», удаление посторонних файлов,
очистку каталогов, отдельный `game/` на сервер, allow-list игровых аргументов и
формат uuid. Тесты с файловой системой и хешированием (`integrity.rs`,
`install_tests.rs`) требуют `cargo test`.

## Секции серверов

Каталог можно разложить по секциям: «Выживание», «Мини-игры», «Наши». Это
**локальная** раскладка игрока и она не входит в контракт провайдера.

- Провайдер присылает плоский список и о секциях не знает: переименовать папку,
  которую создал игрок, он не может.
- Порядок секций — порядок игрока; порядок серверов внутри секции — порядок
  провайдера (другого ранга у лаунчера нет).
- Сервер без секции всегда виден под заголовком «Без секции». Туда попадает
  каждый новый сервер: провайдер добавил сервер — игрок должен его заметить.
- Удаление секции возвращает её серверы в «Без секции». Сами серверы не
  удаляются.
- Раскладка лежит в `settings.json` (`serverLayout`). Испорченный документ
  ремонтируется: дубли идентификаторов, имена с управляющими символами и
  назначения в несуществующие секции отбрасываются, остальные настройки
  (память, Java, язык) остаются.
- Сервер, который провайдер убрал из `config.json`, теряет свою строку в
  раскладке при следующем сохранении.
