# Installation and false-positive remediation roadmap

## Scope and current behaviour

Providers can supply a pinned ZIP or a Modrinth/packwiz source. The installer verifies the ZIP's published digest, indexes extracted files, and verifies source files against their supplied hashes. A local index records what was installed; it does not authenticate a malicious or compromised provider. CurseForge source resolution is **not implemented**: its API and distribution restrictions must be resolved before support is promised.

A Prism instance is not necessarily a complete standalone Minecraft directory: it normally describes components in `mmc-pack.json` and may rely on Prism's shared versions, assets and libraries. The current ZIP inspector reads Mojang version profiles, not Prism component metadata. For a Prism-shaped ZIP without those profiles, it reads the bounded `mmc-pack.json` component list and shows a diagnostic of pinned Minecraft/loader versions, then stops even if the server provides a vanilla hint rather than silently treating the hint as the installed loader. Cached versions are informational, disabled components are excluded from the summary and unknown components are retained. For profile-less exports, a read-only requirements pass retains exact Minecraft, loader and LWJGL pins and rejects ambiguous, unpinned or unsupported requirements and conflicting server version hints; it does not install them. It recognizes both `minecraft/` and `.minecraft/`, including a one-folder wrapper. If a Mojang profile exists alongside the Prism metadata, its pinned Minecraft and loader identity must match; custom `patches/`, unknown active components, unpinned versions and ambiguous dual game directories stop preparation rather than being silently ignored. An active LWJGL pin is also compared to LWJGL Maven coordinates in the selected and inherited vanilla profiles; absent or conflicting evidence blocks preparation. This is an identity check, not verification of the libraries or platform rules. This is a read-only guard, not complete Prism installation support, and a matching identity alone does not verify all required files.

A bounded, read-only asset inventory compares the unique objects listed by a Minecraft asset index against the verified release index. It logs missing and wrong-sized object counts and expected bytes; a size match does not validate the expected SHA-1. When the user selects **prepare in advance** and the verified release contains a readable index, a separate live-game audit hashes matching-sized files against that index's SHA-1, without following symlinks/reparse points. It reports aggregate counts in the launcher log; the extra disk reads can take time. SHA-1 is the Minecraft asset format, not a modern anti-cheat authenticity guarantee. The index inherits only the trust established for the provider's archive, not independent Mojang authentication. An absent or unreadable archive index produces no live audit. For ZIPs, if this audit reports missing or changed assets (during preparation), or the older archive-level checks find gaps, a confirmation is now required before `install_profile` runs. Approval binds the revision, server/instance, versions, loader intent, coarse archive hints, asset totals and operation; it is recomputed on retry. Rejection does not run the supplementary installer. The listed archive gaps are hints, not a complete file-level plan; size and external downloads may be unknown. The ZIP itself is downloaded before the prompt. Approval repeats preparation and can prompt again on later launches because the old archive-based gap detection does not account for every already-installed file. Separate Java-download consent, complete library/native validation and Prism without version profiles remain unfinished. Modrinth and packwiz do not use this ZIP consent branch.

Within one launcher process, preparation now claims the Minecraft instance before resolving or syncing, and direct install/launch refuses that instance until preparation completes. The guard is released on return, including a consent prompt or error. The blocking live-file verification/sync worker retains a shared claim if its awaiting future is cancelled, until the worker exits. Install and start claims are also reference-counted through their blocking Minecraft, loader and Mojang runtime workers, and are released after the last worker exits even if the async caller is cancelled. Windows Java extraction retains its staging directory and installation lock through cancellation. Preparation, direct installation and launch now acquire an advisory file lock on the instance, shared with their blocking workers and retained by the game monitor until the child exits. This coordinates cooperating launcher processes using this version; it cannot stop older versions, other launchers, external file changes, or guarantee protection of an orphaned game if the launcher process crashes. Other cancellation and file-mutation paths still need an audit before automatic Connector-cache quarantine.

The Minecraft path also reacquires the server release lock after installation, checks that `current.json` still identifies the selected release, and holds it through release verification, live sync and pack scanning. If another cooperating update or rollback won the gap, preparation stops and asks for a retry rather than syncing a stale release. The ZIP extraction worker retains that server lock after cancellation until it stops touching staging. Source installs run under a supervisor which receives cancellation if its caller disappears and retains the server lock until active tasks are drained and staging cleanup completes. The in-memory installation registration is released on drop. Full Tokio, Windows and failure-injection validation remain necessary. This does not prevent uncooperative external modification.

## Implementation phases

1. **Plan before downloading:** parse and validate Prism component metadata from the verified ZIP, preserve explicit versions, reject ambiguous or unsupported components, and inventory the actual files needed by that profile (including platform-specific libraries and asset objects). A directory's existence alone is not proof of completeness. Do not execute Java paths or arbitrary commands from `instance.cfg` or pack metadata. Provide a typed, revision-bound preparation plan with missing components, sizes where known, and download sources.
2. **Consent and repair:** show that plan before fetching missing ZIP components; refuse means no component download or installation. On acceptance, revalidate the revision and plan, fetch only missing or invalid files from approved sources, verify expected hashes where available, stage and atomically commit, reuse intact assets and existing loader installations. Do not rerun an installed loader merely because another file is missing. Java is detected separately and a separate installation is offered if necessary. Define an explicit failure when a component cannot be safely verified or repaired.
3. **Source packs:** preserve hash-verified Modrinth/packwiz reuse and the provider's intended version. Research supported CurseForge API credentials, rate limits and third-party distribution restrictions; report unavailable files rather than inventing bypasses. User confirmation policy for source packs must be explicit and distinct from ZIP repair.
4. **Runtime artifacts and false positives:** distinguish verified provider files, personal data and generated caches. Connector's 1.20.1 `.connector/temp` can contain nested jars extracted from verified input; transformed output is executable and cannot be trusted just because of its path or a first-run snapshot. Design provenance and validation or safe regeneration for each artifact class, without deleting personal files or allowing a cache directory to bypass checks. Inspect actual Connector versions and loader discovery rules, including symbolic links and Windows reparse points.
5. **Windows validation:** use representative Prism exports (vanilla, Fabric, Forge, NeoForge), incomplete and complete ZIPs, Modrinth and permitted CurseForge fixtures. Exercise first install, offline/repeat, updates, tampering, corrupted or missing files, consent refusal, interruption/recovery and Connector-generated cache. Record timings and network activity; confirm no accidental reinstallation and preserve worlds/settings.

No phase should treat all files observed after a first game launch as trusted; a crash, unrelated process or malicious file could contaminate that snapshot. Unknown generated artifacts require a clear actionable message, not a silent allowance or deletion.

Prism metadata format researched against Prism Launcher commit `15125f168cb414384e540d6f6370f4868579145a`, `launcher/minecraft/PackProfile.cpp` and `Component.cpp`. No Prism code is copied.
