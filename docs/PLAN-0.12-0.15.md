# План обновления 0.12–0.15: сборки из внешних источников, античит, секции серверов

> **Исторический план, не текущий отчёт о готовности.** Состав и поведение
> изменились после его написания. Актуальные ограничения и незавершённые задачи:
> [INSTALLATION-ROADMAP.md](INSTALLATION-ROADMAP.md),
> [INSTALLATION-AUDIT.md](INSTALLATION-AUDIT.md) и [ANTICHEAT.md](ANTICHEAT.md).
> Исторические списки и утверждения ниже не подтверждают текущие проверки.

Документ о том, что делаем, в каком порядке и почему именно так. Он писан до
кода: решения ниже — это границы задачи, а не пожелания. Отклонение от них
обсуждается отдельно, а не «по ходу».

Ответы заказчика, из которых всё следует:

| Вопрос                | Решение                                                     |
| --------------------- | ----------------------------------------------------------- |
| Packwiz               | И клиент умеет ставить пак напрямую, и есть конвертер в ZIP |
| Modrinth / CurseForge | Modrinth — да; CurseForge — отдельным решением позже        |
| Античит               | Ключевые слова в ресурс-паках **и** блокировка запуска      |
| Секции серверов       | Только игрок, провайдер о них не знает                      |
| Палитра и пресеты     | Убрать изменение палитры целиком                            |

## 0. Что уже есть, чтобы не строить второй раз

- `pack.json` (`src-tauri/src/line/pack.rs`) уже умеет: ссылка на ZIP, sha256,
  размеры, `revision`, кэш последнего удачного манифеста, откат на него при
  сбое сети.
- `integrity.rs` уже хеширует **каждый** файл релиза и удаляет посторонние.
  Это и есть «сканер, который сверяет файлы и убирает изменения» из задачи 2.
- `launch.rs::scan_release_blocking` вызывает этот скан **перед каждым** запуском
  под межпроцессной блокировкой.
- `minecraft.rs::mc_play` уже делает: `pack.toml`-подобный манифест → скачать →
  распаковать → проверить → `pack::inspect` (какой загрузчик и версия) →
  докачать недостающее из официальных хостов Mojang/загрузчиков →
  `sync_game_dir` в `game/` → запуск.
- `storage.rs` — атомарная запись, приватные каталоги, отказ от симлинков.

Вывод: источник сборки — это **новый способ получить набор файлов**, а не новый
установщик. Всё, что идёт после «файлы получены и проверены», переиспользуется
без изменений. Это главное ограничение плана: ни один новый источник не получает
свой путь распаковки, свой запуск или свой способ проверки.

## 1. Источники сборок (задача 1)

### 1.1 Единая модель

Новый модуль `src-tauri/src/line/source/`:

```
source/
  mod.rs        enum Source + resolve() -> ResolvedPack
  packwiz.rs    pack.toml → index.toml → files/*.pw.toml   (TOML)
  modrinth.rs   modrinth.com/modpack/<slug> → .mrpack       (JSON)
```

```rust
pub enum Source {
    /// Сегодняшний ZIP + pack.json. Остаётся по умолчанию: старые конфиги
    /// обязаны работать без правок.
    Archive { distribution: Distribution, manifest_url: Option<String> },
    /// Raw-ссылка на pack.toml в GitHub (или любом HTTPS-хосте).
    Packwiz { pack_toml_url: String },
    /// Официальная страница или API-ссылка Modrinth.
    Modrinth { project: String, version: Option<String> },
}

/// Что в итоге скачалось и чем это проверяется. Ровно то, что сегодня ждёт
/// `download_and_extract`; поэтому остальной конвейер не меняется.
pub struct ResolvedPack {
    pub revision: String,          // sha256 нашего собственного манифеста
    pub files: Vec<PackFile>,      // путь, url, sha256, размер — уже проверенные
    pub overrides: Option<PathBuf>,// packwiz/Modrinth: файлы поверх
    pub minecraft_version: Option<String>,
    pub loader: Option<(LoaderChoice, String)>,
}
```

Контракт один: **любой источник обязан выдать `PackFile` с sha256 на каждый
файл**. Где источник не даёт хеш (packwiz без `hash` в `.pw.toml`), файл
скачивается и хешируется на месте, а хеш фиксируется в нашем манифесте — после
первой установки он становится таким же жёстким, как у ZIP. Исключений нет:
«источник, которому можно верить на слово» не появится.

### 1.2 Packwiz

Читаем по спецификации packwiz, только нужное:

- `pack.toml`: `index.file`, `index.hash-format`, `index.hash`,
  `versions.minecraft`, `versions.fabric|quilt|forge|neoforge`.
- `index.toml`: список `[[files]]` с `file` и `hash` — это **метаданные**;
  сами моды лежат рядом как `mods/<name>.pw.toml`.
- `.pw.toml`: `filename`, `download.url` (+ `hash-format`/`hash`),
  `side` (`client`/`server`/`both`) — серверные и необязательные не скачиваем.
- `overrides/` и `config/` — копируются как есть, тоже с хешами.

Правила:

1. `hash-format` поддерживаем `sha256` и `sha512` (первый нормализуем в sha256,
   второй тоже — пересчётом, не доверием). Остальные (`md5`, `sha1`, `murmur2`)
   **отклоняем конфигом**: слабый хеш в античите хуже его отсутствия.
2. `download.url` обязателен HTTPS; `mode` = `metadata:curseforge` **не
   поддерживается** в этой версии — это как раз путь, требующий ключа
   CurseForge. Сообщение об ошибке называет файл и причину, а не «не удалось».
3. Относительные пути `index.file` и `[[files]]` резолвим относительно URL
   `pack.toml` и **проверяем, что итоговый URL остался на том же хосте**:
   packwiz разрешает ссылки на другие хосты, но не через редирект из нашего
   парсера. Внешние ссылки (`download.url`) — отдельный случай, они и так на
   CDN модов; для них — только HTTPS и наш обычный `http::get`.
4. `pack-format` проверяем: `packwiz:` + semver; major выше нашего — понятная
   ошибка «обновите лаунчер», а не частичная установка.
5. Хеш самого `index.toml` сверяем с `pack.toml`. Если не сходится — стоп:
   это ровно тот случай, когда по ссылке лежит не то, что задумал автор.

Конвертер `scripts/pack-from-packwiz.mjs` (вторая половина ответа «оба»):

```
node scripts/pack-from-packwiz.mjs <pack.toml-url|каталог> --out pack.zip \
  --pack-json https://cdn.example.com/pack.json
```

Скачивает по тем же правилам, складывает в ZIP в той же раскладке, что и
`build-pack.mjs`, и печатает `pack.json` с sha256. Нужен провайдерам, которые
хотят раздавать один архив (и для демо-CI без сети): конвертер и клиент обязаны
давать **идентичный** набор файлов — это проверяется общим тестом на фикстуре.

### 1.3 Modrinth (CurseForge — позже)

- Вход: `https://modrinth.com/modpack/<slug>` **или** `modrinth.com/modpack/<slug>/version/<id>`.
  Разбираем URL строго: host `modrinth.com` (и `www.`), путь
  `/modpack/<slug>[/version/<id>]`, slug — наш `validate_slug`.
- API: `api.modrinth.com/v2/project/<slug>/version` (или `/version/<id>`),
  берём последнюю **release**-версию, не snapshot/beta: бета-сборка в
  продакшене — это чужие баги у игрока.
- Скачиваем `.mrpack` (это ZIP): внутри `modrinth.index.json` и `overrides/`.
  `files[]` уже содержит `path`, `downloads[]` и `hashes.sha512` — sha512
  проверяем **до** распаковки, sha1 игнорируем.
- `dependencies.minecraft` и `dependencies.fabric-loader` и т.п. дают версию и
  загрузчик: то, чего ZIP-пути сегодня не хватает и что заполняется `inspect`.
- CurseForge: **не входит**. Причина не в лени: у CurseForge официальный API
  требует `x-api-key`, а ключ в скачиваемом лаунчере видят все. Это отдельное
  решение (свой прокси у провайдера / ключ, вводимый игроком / отказ), и
  принимать его в этом обновлении нельзя — оно меняет модель угроз.

### 1.4 Конфиг провайдера (обратная совместимость)

```jsonc
{
  "id": "survival",
  "distribution": { "url": "https://cdn.example.com/pack.zip" }, // как было
  "source": {
    // новое, опционально
    "kind": "packwiz",
    "pack_toml_url": "https://raw.githubusercontent.com/acme/pack/main/pack.toml",
  },
}
```

- Нет `source` → всё работает как в 0.11. `distribution` у таких серверов
  остаётся обязательным (как сейчас), чтобы старый конфиг не сломался.
- Есть `source` → `distribution` можно не указывать. Валидатор требует **ровно
  одно** из двух и отвергает оба сразу: два источника на один сервер — это
  неоднозначность, которая проявится у игрока, а не при публикации.
- `required_features` получает `packwiz-v1` и `modrinth-v1`: конфиг с ними
  отвергается **старым** лаунчером с внятным сообщением, а не падает на
  середине установки.
- `pack_manifest_url` остаётся только у `Archive`; с `source` он запрещён.

### 1.5 Что игрок видит

- В карточке сервера и на экране сервера — откуда сборка: «ZIP», «packwiz»,
  «Modrinth», с версией/ревизией источника.
- Прогресс: «Проверка pack.toml» → «Скачивание модов 12/84» → «Проверка
  хешей» → «Распаковка overrides» → «Проверка файлов экземпляра» → запуск.
  Для ZIP-пути — как сейчас.
- Ошибка называет файл: `mods/create-1.21.1.jar: ссылка ведёт на HTTP` — а не
  «ошибка установки».

## 2. Античит (задача 2)

Сегодняшний скан покрывает **релиз** (immutable, только для чтения). Живой
`game/` — нет: `sync_game_dir` копирует файлы только при смене ревизии, а потом
игрок и моды пишут в `game/` свободно. Игрок, который «поставил себе xray»,
кладёт его в `game/mods` или `game/resourcepacks` — и сегодня лаунчер этого не
видит. Значит, одной проверки ресурс-паков мало: нужен скан живого каталога.

### 2.1 Три уровня, каждый со своей ценой

| Уровень    | Что проверяем                                                                             | Цена                                        | Когда                                                        |
| ---------- | ----------------------------------------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------ |
| L1 (есть)  | Хеши файлов релиза, посторонние удаляются                                                 | уже есть                                    | перед каждым запуском                                        |
| L2 (новое) | `game/mods` и `game/resourcepacks`: файл, которого нет в `pack-state.json`, — посторонний | список путей, без хеширования содержимого   | перед каждым запуском                                        |
| L3 (новое) | Содержимое ресурс-паков на ключевые слова                                                 | открыть ZIP и прочитать имена + JSON/тексты | перед первым запуском ревизии + по кнопке «Проверить сейчас» |

L2 — дешёвый и главный: он ловит и jar-читы, и подменённые ресурс-паки,
потому что сравнивает **пути и размеры** с тем, что опубликовал провайдер.
L3 — то, что просили: слова внутри ресурс-паков. L2 без L3 уже отсекает
большую часть, L3 ловит то, что пришло **в составе** легальной сборки.

### 2.2 Сканер ключевых слов

`src-tauri/src/line/resourcepack.rs`:

- Вход: ZIP ресурс-пака (и `.zip` в `game/resourcepacks`, и
  `releases/<sha>/resourcepacks/*.zip`).
- Читаем **только** имена файлов и небольшие текстовые/JSON-файлы
  (`assets/**/*.json`, `pack.mcmeta`, `*.mcmeta`, `*.txt` до 256 КиБ каждый,
  суммарный бюджет 8 МиБ, лимит 50 000 записей — те же границы, что у
  распаковщика). PNG **не** декодируем: смотреть в пиксели — это уже не
  «ключевые слова», а эвристика, которая даёт ложные срабатывания.
- Список ключевых слов — данные, не код: `src-tauri/src/line/cheats.txt`
  (вкомпилирован через `include_str!`), по строке на слово, `#` — комментарий.
  Нижний регистр, сравнение по границам: `xray` ловит `xray`, `XRay`,
  `xray_ultimate`, но не `xrayed_note`. Категории: `xray`, `freecam`, `fly`,
  `noclip`, `fullbright`, `esp`, `killaura`, `reach`, `autoclicker`.
- Результат: `Vec<Finding> { file, entry, keyword, category }`, а не булево
  «чисто/нечисто»: игроку надо объяснить, что именно нашли.

Список — самая спорная часть, и она должна быть **редактируемой**: у провайдера
свой pack, свои моды, свои ложные срабатывания. Поэтому:

```jsonc
"anticheat": {
  "scan_resourcepacks": true,      // default true
  "extra_keywords": ["mymod-xray"],// только добавлять, не убирать
  "allow": ["resourcepacks/official-hud.zip"]  // исключение по sha256, не по имени
}
```

`allow` — по **sha256**, а не по имени: исключение по имени обходится
переименованием. Список `extra_keywords` не может ослабить базовый: удалить
слово из базового списка конфигом нельзя.

### 2.3 Что происходит при находке (ответ «блокировка»)

1. Ресурс-пак **не удаляем**: файл может быть легальным, а слово — ложным
   срабатыванием, и молча стирать чужой файл нельзя.
2. Запуск **останавливается**. В `GamePhase` добавляется `Blocked`, в UI —
   экран «Запуск остановлен»: файл, запись, слово, что делать (удалить пак,
   написать провайдеру).
3. Две кнопки: «Удалить и продолжить» (удаляет именно этот файл, повторный
   скан и запуск) и «Отправить провайдеру» (тот же `mailto:` с диагностикой,
   что в 0.11) — второй путь для ложного срабатывания.
4. Запись в `launcher_logs`: `WARN anticheat resourcepack-blocked file=… keyword=…`.
5. Если провайдер выключил `scan_resourcepacks`, кнопки блокировки нет, но L2
   (посторонние файлы) остаётся — выключить L2 нельзя, это и есть защита.

### 2.4 Чего античит **не** обещает

Честно и в документации, и в интерфейсе: это защита от «поставил чит себе в
папку», а не от подмены процесса во время игры. `-javaagent` и правка JVM
запрещены `launch_manifest`, аргументы проверяются, но лаунчер не может
гарантировать, что игрок не запустил игру в обход него. Обещать «полный
античит» было бы ложью, которую первый же школьник опровергнет.

## 3. Секции серверов (задача 3)

Решение заказчика: **секции задаёт только игрок**, провайдер о них не знает.

Значит, это локальная функция, и она **не касается контракта провайдера**:

- `settings.json` получает `serverLayout`:
  ```jsonc
  {
    "sections": [
      { "id": "fav", "name": "Мои", "collapsed": false },
      { "id": "survival", "name": "Выживание", "collapsed": true },
    ],
    "assign": { "survival-main": "fav", "creative": "survival" },
    "order": { "fav": ["survival-main"], "": ["skyblock"] },
  }
  ```
  `""` — секция «Без секции», она всегда есть и не удаляется. Имена — текст
  игрока, ограничение 40 символов, без control-символов.
- Сервер, удалённый провайдером, из раскладки вычищается при следующем
  сохранении: раскладка не должна накапливать мусор.
- UI: заголовок секции — кнопка со стрелкой (свернуть), счётчик серверов,
  «…» — переименовать, удалить секцию (серверы возвращаются в «Без секции»),
  «Добавить секцию». На карточке/экране сервера — выбор секции (Select).
  Перетаскивание серверов между секциями — **не в этой итерации**: сначала
  рабочая структура, потом drag. Управление с клавиатуры — обязательно, у
  перетаскивания его придётся делать отдельно.
- Секции не влияют на установку, запуск и сессии: это чистая раскладка списка.
- Проверка: `serverLayout` — отдельный тип, который переживает повреждённый
  JSON (как `settings.json` сейчас: битый файл → значения по умолчанию, не
  падение).

Альтернатива, которую **отклонили**: секции в конфиге провайдера. Она звучит
удобнее (провайдер сам группирует свои серверы), но тогда порядок и названия
диктует провайдер, а игрок не может ни переименовать «Выживание» в «Наши», ни
убрать пустую секцию. Заказчик выбрал игрока, и это же снимает с контракта
провайдера лишнюю версию схемы.

## 4. Палитра и пресеты (задача 4)

Убираем **изменение палитры**: `preset`, `palette` и `branding/presets.json`
уходят. Остаются продукт, ассеты, атрибуция.

Что меняется:

| Было                                                              | Станет                                                                                                                |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `branding/presets.json` с 6 палитрами                             | удалён                                                                                                                |
| `line.brand.json` → `preset`, `palette`                           | удалены из схемы; их наличие — ошибка сборки с объяснением                                                            |
| `brand-config.ts`: `validateColor`, `renderCss`, слияние пресетов | удалены; `renderCss` больше не генерирует `:root`                                                                     |
| `src/brand/generated.css`                                         | остаётся, но пустой (шапка + комментарий «токены Obsy, перекраска запрещена») — файл импортируется из `src/index.tsx` |
| `BrandConfig` тип                                                 | без `preset`/`palette`                                                                                                |
| Тесты `brand.test.ts` (46 упоминаний)                             | переписаны: палитра не настраивается, попытка задать цвет — ошибка                                                    |
| `docs/BRANDING.md`, `BUILD.md`, `START.md`, `VERIFICATION.md`     | разделы про пресеты заменены правилом «палитра фиксирована»                                                           |

Почему так, а не «оставить один пресет obsy»: поле `preset: "obsy"` без
альтернатив — это приглашение добавить вторую палитру в следующем релизе. Мы
убираем механизм, а не его текущее значение. И цена ошибки видна сразу: старая
сборка с `preset` теперь падает на `npm run brand` с текстом, объясняющим, что
палитра больше не настраивается.

Не трогаем: `AnimatedBackdrop` (`palette` в `backdrops.ts` — это цвета фонов,
а не интерфейса), `Attribution`, `product`, иконки. Атрибуция остаётся
обязательной — это лицензионное требование, и оно не про цвета.

## 5. Порядок работ и версии

Каждый этап — отдельная ветка и отдельный PR, каждый заканчивается зелёными
`npm test`, `npm run build`, `brand:check`, `version:check` и (в CI)
`cargo check/test/clippy`.

| Этап | Версия | Содержание                                | Почему в этом порядке                                                                                                 |
| ---- | ------ | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 0    | 0.12.0 | Палитра: удаление пресетов                | Самое маленькое, независимое, и освобождает `brand-config.ts` от кода, который иначе пришлось бы трогать в этапах 1–3 |
| 1    | 0.13.0 | Секции серверов                           | Только фронтенд + `settings.json`, не ждёт Rust вообще                                                                |
| 2    | 0.14.0 | Античит: L2 + L3, `Blocked`               | Нужен до источников: пак из packwiz приносит чужие ресурс-паки, и проверять их надо с первого дня                     |
| 3    | 0.15.0 | Источники: packwiz + Modrinth + конвертер | Самое большое; опирается на 2 (файлы из новых источников сразу проверяются)                                           |
| 4    | 0.15.x | CurseForge                                | Отдельно: требует решения по ключу API                                                                                |

Почему античит раньше источников: packwiz и Modrinth приносят файлы из чужих
CDN. Если сначала включить источники, между релизами будет окно, где лаунчер
ставит непроверенное. Пусть лучше окно будет у ZIP, который уже проверяется
хешами.

## 6. Риски и как их снимаем

1. **packwiz меняет формат.** `pack-format` семвер — контракт: major выше
   нашего отклоняем с внятным сообщением. Фикстуры лежат в репозитории, а не
   тянутся из сети в тестах.
2. **Modrinth API недоступен из России/по сети.** Кэш последнего удачного
   `.mrpack`-манифеста, как у `pack.json` сейчас; понятная ошибка сети без
   потери уже установленной сборки.
3. **Ложные срабатывания античита.** Уровень L3 — предупреждение с
   объяснением и кнопкой «Отправить провайдеру»; исключение по sha256; список
   слов расширяем конфигом. L2 (посторонние файлы) — жёсткий, но он про файлы,
   которых провайдер не публиковал: тут ложных срабатываний быть не может.
4. **Блокировка запуска ломает игру.** Тест: заблокированный запуск не
   занимает `InstallLock`, не оставляет аренду и не стирает файлы.
5. **Секции ломают сохранение настроек.** `serverLayout` проходит через ту же
   схему `settings.json` с откатом к умолчаниям; отдельный тест на битый JSON.
6. **Удаление палитры ломает чужие сборки.** Старый `line.brand.json` падает
   на `npm run brand` с текстом «палитра больше не настраивается, удалите
   preset/palette» — сборка не собирается молча без цвета.

## 7. Ограничения этой среды (честно)

- **Rust здесь не компилируется**: нет `rustc`/`cargo`, а `static.rust-lang.org`
  и `crates.io` из песочницы недоступны. Поэтому этапы 2 и 3 проверяются
  tree-sitter-разбором, чтением, юнит-тестами «чистых» функций на Node (где
  логика выносима) и мутациями, а `cargo check/test/clippy` — в CI или у вас.
  Это тот же режим, в котором делался 0.11, и он ловит синтаксис и логику
  тестами, но не типы.
- `npm run demo` здесь не стартует (нужен Rust); UI проверяется рендером того
  же бандла с моком IPC.
- CurseForge не входит ни в один этап: нужен ваш ответ по ключу API.
