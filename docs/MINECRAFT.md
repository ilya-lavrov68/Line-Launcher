# Режим Minecraft через `mc-launcher-core`

Отдельный режим рядом с провайдерскими ZIP-сборками. Провайдер, ticket-канал,
гардероб и демо работают как раньше: профили Minecraft живут в
`<app-data>/minecraft/<instanceId>/` и не пересекаются с `instances/<server>/`.

Крейт: [`mc-launcher-core` 0.1.2](https://docs.rs/mc-launcher-core), MIT,
исходники — [Star-tears/mc-launcher-core](https://github.com/Star-tears/mc-launcher-core).
В `Cargo.toml` версия закреплена как `=0.1.2`: фасад 0.1.x ещё меняется, а
`minecraft.rs` разбирает `LauncherError` исчерпывающим `match`.

## Для каких серверов этот режим

Лаунчер делается под **серверы с `online-mode=false`**: они не проверяют сессию
Mojang, поэтому автономный аккаунт — штатный и правильный способ входа. Никакой
Microsoft-логики в режиме нет и не планируется: `auth::microsoft_account` из
крейта не вызывается, `Account::Microsoft` не конструируется, authlib-инъекторы
не используются. Регрессионный тест это фиксирует.

| Возможность                      | Поведение                                                          |
| -------------------------------- | ------------------------------------------------------------------ |
| Ваш сервер (`online-mode=false`) | вход под ником аккаунта проекта                                    |
| Автозаход после «Играть»         | сразу на сервер, без главного меню                                 |
| Одиночная игра                   | не предлагается лаунчером: кнопки «Одиночная игра» в потоке нет    |
| Серверы с `online-mode=true`     | не поддерживаются: они проверяют сессию, лаунчер её не подделывает |

**Про кнопку «Одиночная игра» честно.** В ванильном клиенте нет аргумента
командной строки, который её убирает (`--disableMultiplayer` и `--disableChat`
делают обратное — режут мультиплеер, они выключены). Автозаход через Quick Play
пропускает главное меню целиком, но если игрок нажмёт Esc → «Выйти в главное
меню», кнопка там останется. Чтобы убрать её физически, нужен клиентский мод в
сборке — это отдельная задача, могу сделать небольшой Fabric-мод.

## Как провайдер включает режим

Единственный способ — `"launch_mode": "minecraft"` у сервера, плюс
`server_address` и `minecraft_version`. Конфиг без этого поля не меняет
поведение: режим не включается ни наличием адреса, ни `required_features`, ни
версией лаунчера.

Страница сервера такого типа показывает панель Minecraft вместо док-панели
ZIP-сборки. Она вызывает:

| Команда                   | Когда                                                                   |
| ------------------------- | ----------------------------------------------------------------------- |
| `mc_status`               | при открытии страницы — восстановить «игра запущена» после смены экрана |
| `mc_list_installed`       | доступен через API; список профилей не выводится в панели запуска       |
| `mc_play`                 | кнопка «Играть»: проверить/скачать, синхронизировать, запустить и зайти |
| `mc_play` с `prepareOnly` | «Подготовить заранее»: та же сборка и профиль, но без запуска           |
| `mc_install`              | отдельная низкоуровневая установка только профиля Minecraft, без сборки |
| `mc_stop`                 | «Остановить игру»; фаза `exited` приходит событием, а не ответом        |

`mc_launch` в интерфейсе намеренно не используется: он запускает профиль без
сверки с опубликованной сборкой, и единственный корректный путь «просто играть» —
`mc_play`. Команда остаётся в API для будущего экрана выбора версии/загрузчика.

События `line://mc-install-progress` и `line://mc-game-status` фильтруются по
`instanceId`, поэтому два сервера в одном окне не перепутают прогресс.

## Автозаход на сервер

Mojang **удалил `--server` и `--port` в 23w14a** (1.20), заменив их Quick Play.
Крейт всё ещё добавляет старую пару через `LaunchOptions::server`, и современные
клиенты её молча игнорируют — автозахода не происходит. Поэтому:

- `LaunchOptions.server` остаётся `None`;
- поддержка определяется по метаданным: `game_argument_tokens` собирает все
  токены `arguments.game`, включая rule-gated, и `has_quick_play_token` ищет
  **точное** совпадение с `--quickPlayMultiplayer` (подстрока ошибочно приняла бы
  `--quickPlayMultiplayerLegacy`);
- `load_version` уже склеил `inheritsFrom`, так что профиль Fabric/Forge
  наследует признак поддержки от ванильного клиента;
- `ensure_server_join` добавляет `--quickPlayMultiplayer host:port` для 1.20+ и
  `--server host --port port` для более старых версий, никогда не дублируя пару.

Адрес берётся из `server_address` в конфиге провайдера (`host`, `host:port` или
`[ipv6]:port`, порт по умолчанию 25565) и проверяется до запуска: пробелы,
управляющие символы и ведущий дефис отклоняются, чтобы адрес не превратился в
ещё один флаг клиента.

## Сборка — это ZIP целого экземпляра

Провайдер архивирует свой `.minecraft` и кладёт архив на сервер. Лаунчер принимает
именно это, а не «список модов, которые надо собрать»:

- в корне архива может быть сама папка игры (`mods/`, `config/`, `versions/`,
  `libraries/`, `assets/`, `options.txt`), либо обёртка `.minecraft/`,
  `minecraft/` или один именованный каталог — `instance::find_game_prefix`
  находит её по маркерам, порядок кандидатов фиксирован;
- версия берётся из `versions/<id>/<id>.json`. Если профилей несколько, сначала
  учитывается подсказка, прямо называющая профиль лоадера, затем единственный
  профиль с лоадером. Подсказка базовой версии не подавляет его; если лоадеров
  несколько, требуется указать профиль явно. Несовпадение базовой версии с
  найденным ванильным профилем — ошибка, а не случайный выбор;
- лоадер определяется по Maven-координатам (`net.fabricmc:fabric-loader`,
  `org.quiltmc:quilt-loader`, `net.minecraftforge:fmlloader`,
  `net.neoforged:neoforge`). Main class — только подсказка: Forge и NeoForge
  делят `cpw.mods.bootstraplauncher`, поэтому по нему одному их не различить.
  Quilt важнее Fabric, потому что Quilt-экземпляр законно несёт Fabric-библиотеки;
- базовая ванильная версия читается из `inheritsFrom`/`jar`, поэтому профиль
  `fabric-loader-0.16.9-1.21.1` корректно раскладывается на «1.21.1 + Fabric»;
- чего в архиве нет (`client-jar`, `libraries`, `asset-index`, `assets`) —
  докачивается крейтом с официальных серверов Mojang. Архив только с модами
  тоже работает: тогда версия и лоадер берутся из конфига провайдера;
- лоадер, найденный внутри, используется как есть; лоадер из конфига ставится
  только если внутри его нет.

### pack.json

Рядом с архивом лежит маленький JSON — по нему лаунчер понимает, обновилась ли
сборка, не скачивая гигабайты:

```json
{
  "schema_version": 1,
  "url": "https://cdn.example.com/pack.zip",
  "sha256": "…64 hex…",
  "size_bytes": 734003200,
  "unpacked_size_bytes": 1610612736,
  "revision": "1.0.0",
  "minecraft_version": "1.21.1"
}
```

Адрес этого файла — `pack_manifest_url` у сервера в `config.json`. Блок
`distribution` остаётся запасным вариантом для провайдеров без pack.json.
Сгенерировать файл из готового архива:

```bash
npm run pack:manifest -- pack.zip https://cdn.example.com/pack.zip --revision 1.0.0
```

Скрипт читает центральный каталог ZIP (без зависимостей), считает sha256 и
распакованный размер, проверяет те же лимиты, что и лаунчер (4 ГиБ архив,
16 ГиБ распаковано, 50 000 файлов), и заодно говорит, найдена ли папка игры и
сколько в ней профилей версии. Загружать на сервер нужно **оба** файла: архив и
pack.json. Если обновить архив, но забыть pack.json, лаунчер честно скачает
старый sha256 и отклонит архив как повреждённый.

При недоступности сети используется последняя удачная копия pack.json
(`pack-manifest.json` в папке сервера). Если же пришёл битый JSON — это ошибка
провайдера, она не прячется за кэшем.

## Одно нажатие «Играть»

Команда `mc_play({ serverId })` делает всё по порядку:

1. читает `pack.json` и подставляет актуальные url/sha256/размеры;
2. `install::download_and_extract` — скачивает архив **или** подтверждает, что
   установлен тот же самый: если sha256 в квитанции совпал, возвращается
   существующая квитанция (`already_installed`), без перекачивания;
3. `pack::inspect` читает оглавление проверенного архива и JSON версий,
   `pack::sync_game_dir` переносит сборку в живой `.minecraft`;
4. `install_profile` докачивает только недостающее (и ставит лоадер, только если
   его нет внутри);
5. запуск с автозаходом на сервер — без главного меню; `testMode` оставляет игру в меню, а `prepareOnly` завершает работу до запуска.

Для Modrinth и packwiz запуск запрашивает свежие корневые метаданные и сверяет их с сохранённой идентичностью источника. Если она совпадает, а опубликованный релиз и его индекс проходят полную проверку, повторная загрузка не нужна. Старая установка без записи идентичности один раз загружается заново. Изменение источника, профиля или повреждение релиза запускает установку заново; пока она не инкрементальная. При недоступном источнике актуальность не подтверждается, поэтому офлайн-запуск через этот путь не гарантируется.

Прогресс идёт в `line://mc-install-progress` (стадии `resolve`, `download`,
`verify`, `extract`, `commit`, `cached`, дальше стадии крейта) и дублируется в
обычный `line://install-progress`; счётчик файлов и проценты относятся к текущему этапу, а не ко всей установке; общее время завершения не вычисляется. Состояние игры — в `line://mc-game-status`.

### Две папки и что переживает обновление

| Папка                             | Кто владеет | Что происходит                                                          |
| --------------------------------- | ----------- | ----------------------------------------------------------------------- |
| `servers/<id>/releases/<sha256>/` | лаунчер     | распакованный архив, проверяется по хешам, игрок туда не пишет          |
| `minecraft/<instance>/game/`      | игра        | живой `.minecraft`: сюда копируется сборка, здесь миры, логи, настройки |

Правила переноса:

- если sha256 не изменился, копирования нет вообще — значит ваши правки конфигов
  модов остаются нетронутыми;
- при новой ревизии файлы сборки перезаписываются, а `options.txt`,
  `optionsof.txt`, `servers.dat`, `usercache.json` копируются только если их ещё
  нет — настройки графики и список серверов не сбрасываются;
- удаляются только те файлы, которыми владела прошлая ревизия сборки и которых
  нет в новой. `saves/`, `logs/`, `screenshots/`, `crash-reports/`, `shaderpacks/`,
  `journeymap/`, `XaeroWaypoints/`, `.fabric/` и другие пользовательские папки не
  удаляются никогда;
- каждый путь проходит тот же `safe_entry_path`, что и распаковка архива;
  копирование идёт через временное имя, поэтому оборванный запуск не оставит
  половину мод-jar как «готовый» файл.

Честная цена такого разделения: сборка лежит на диске дважды (проверенный архив
и живая копия). Это осознанный обмен диска на то, что игра не может испортить
проверяемую копию.

## Как это устроено

| Шаг             | Код                                    | API крейта                                                                                                                           |
| --------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Инициализация   | `instance_root` + `Launcher::new(dir)` | `launcher::Launcher`                                                                                                                 |
| Установка       | `mc_install`                           | `install_with_progress(InstallRequest, reporter)`                                                                                    |
| Загрузчик модов | `loader_spec`                          | `LoaderSpec::{Fabric,Quilt,Forge,NeoForge}`, `LoaderVersion::{LatestStable,Exact}`; NeoForge 1.20.1: отдельный путь установщика 47.x |
| Метаданные      | `start_game`                           | `load_version` → `VersionJson` (с учётом `inheritsFrom`)                                                                             |
| Команда         | `start_game`                           | `build_launch_command_from_version(&version, LaunchOptions)`                                                                         |
| Процесс         | `tokio::process::Command`              | `LaunchCommand { executable, args, working_dir, env }`                                                                               |

Три особенности крейта, которые учтены в коде:

1. **Он блокирующий.** Внутри `reqwest::blocking`, поэтому каждый вызов обёрнут в
   `tokio::task::spawn_blocking`. Прямой вызов из async-воркера Tauri паникует с
   «cannot block the current thread from within a runtime».
2. **`JavaInstallPolicy::Auto` не ставит Java.** Документация крейта: «The crate
   does not currently bundle or manage a production Java runtime for the new
   facade». Политика оставлена `Auto` ради совместимости, а рантайм реально
   выбирается в `resolve_java` и передаётся через `LaunchOptions::java_executable`.
3. **В `LaunchOptions` нет памяти.** `-Xmx`/`-Xms` приходят из метаданных версии,
   поэтому `apply_heap` заменяет их на значение из настроек ровно один раз.

### Идентичность игрока

`Account::offline("Nick")` создаёт **случайный UUID при каждом вызове** — миры теряли бы владельца. Поэтому используется публичный вариант:

```rust
Account::Offline { username: account_name, uuid: account_uuid }
```

где `account_uuid = player_uuid(&username)` — тот же стабильный идентификатор,
что и в провайдерском режиме. Ник берётся из аккаунта проекта, вход обязателен.

### Java

`resolve_java` идёт по порядку и останавливается на первом подходящем:

1. путь, выбранный игроком в настройках (проверяется запуском `java -version`). Для запуска игры допускается вручную выбранная Java не ниже требуемой: например, Java 21 при требовании Java 17. Это не гарантия совместимости модов. Для внешнего legacy-инсталлятора NeoForge по-прежнему требуется точная Java 17;
2. локальный поиск `java::discover(required_major)`;
3. на Windows x64 для Java 8, 17, 21 и 25 — проверенный кэш Eclipse Temurin или автоматическая загрузка с GitHub;
4. на остальных платформах и для остальных версий — уже скачанный JRE Mojang или `runtime::install_jvm_runtime`, если манифест Minecraft указал компонент.

`required_major` и `component` для игры берутся из `VersionJson::java_version`. Автоматическое обнаружение и скачанный рантайм по-прежнему требуют точное совпадение мажора. Только явно выбранная игроком более новая Java используется как override при запуске игры. Лаунчер не гарантирует, что она совместима с загрузчиком и всеми модами.

### Защита

Метаданные версий скачиваются, а профили загрузчиков пишутся инсталляторами, поэтому
перед запуском аргументы проходят `reject_dangerous_args`: запрещены `-javaagent`,
`-agentlib`, `-agentpath`, `-Xbootclasspath`, `--patch-module`,
`--upgrade-module-path`, `-Djava.system.class.loader` и любое `-DlineLauncher.*`
(пространство приватного IPC провайдерского режима). Идентификатор экземпляра и
версии проверяются как имена каталогов: без `..`, разделителей и управляющих символов.

## Команды Tauri

| Команда             | Аргументы                                            | Результат                   |
| ------------------- | ---------------------------------------------------- | --------------------------- |
| `mc_install`        | `request: { instanceId, minecraftVersion, loader? }` | `{ instanceId, versionId }` |
| `mc_list_installed` | `instanceId`                                         | `string[]`                  |
| `mc_launch`         | `request: { instanceId, versionId }`                 | `McGameStatus`              |
| `mc_stop`           | `instanceId`                                         | `boolean`                   |
| `mc_status`         | `instanceId`                                         | `McGameStatus`              |

События: `line://mc-install-progress` и `line://mc-game-status`. Обёртки —
`lineApi.mcPlay/mcInstall/mcLaunch/mcStop/mcStatus/onMcProgress/onMcGame`.
Кнопка «Играть» вызывает `mcPlay`.

`versionId` из `mc_install` надо сохранять: с загрузчиком это не исходная версия
(`fabric-loader-0.16.9-1.21.1` вместо `1.21.1`).

Лог игры: `<app-data>/minecraft/<instanceId>/logs/launch.log`. Данные игрока —
каталог `game/` рядом с `versions/`, он не удаляется при обновлении профиля.

## Ограничения текущей реализации

- **Отмена работает только на этапе архива.** Скачивание и распаковка ZIP идут
  через обычный конвейер, поэтому `cancel_install(operationId)` их прерывает.
  Докачивание недостающего крейтом отменить нельзя: `install_with_progress` не
  даёт точки отмены, его можно только дождаться.
- **Интерфейс ещё не подключён.** Бэкенд, команды и типизированные обёртки
  готовы; экран выбора версии/загрузчика — следующий шаг.
- Forge и NeoForge запускают java-инсталлятор и ставятся заметно дольше, чем
  vanilla/Fabric/Quilt. Если лоадер уже есть в архиве, инсталлятор не нужен вовсе.
- Сборка занимает место дважды: проверенная распакованная копия и живой
  `.minecraft`. Миры и логи живут только в живом каталоге.
- Кнопку «Одиночная игра» ванильный клиент убрать не даёт: автозаход пропускает
  меню, но после выхода в меню кнопка остаётся. Нужен клиентский мод.

## Проверка

- `npm run test:rust` — чистые правила режима (`validate_version_id`,
  `validate_loader`, `apply_heap`, `reject_dangerous_args`) исполняются настоящим
  `rustc`, 4 новых теста.
- `npm test` — `tests/minecraft-mode.test.ts`: закрепление версии, импорт прелюдии
  без подмены `Result`, все блокирующие вызовы внутри `spawn_blocking`, стабильный
  UUID, порядок выбора Java, аргументы/env/cwd/kill switch, регистрация команд и
  аддитивная граница с провайдерским режимом.
- Обращение к API крейта дополнительно проверялось компиляцией стендом с точными
  сигнатурами 0.1.2. **Это не заменяет `cargo check`**: полный граф зависимостей
  в среде разработки не собирается.

На своей машине:

```powershell
cargo check --manifest-path src-tauri/Cargo.toml --all-targets
cargo test --locked --manifest-path src-tauri/Cargo.toml
```

**Про `Cargo.lock`.** Новая зависимость в лок-файл ещё не внесена: в среде
разработки нет доступа к crates.io. Первый `cargo check` **без** `--locked`
обновит `src-tauri/Cargo.lock` сам — этот файл нужно закоммитить, иначе CI и
`cargo test --locked` упадут на «lock file needs to be updated».

Первая сборка добавляет зависимости крейта (`zip 2.x`, `sha2 0.11`, `xz2`,
`chrono`, `rand`, `which`) — это нормально, они сосуществуют с текущими версиями
лаунчера, потому что мажоры разные.

### Автоматическая Java на Windows x64

Если подходящей локальной Java нет, лаунчер сам устанавливает приватную JRE Eclipse Temurin нужной версии (8, 17, 21 или 25), в том числе Java 17 для Minecraft 1.20.1. Системная Java не заменяется, права администратора не нужны. Перед запуском проверяются размер и SHA-256 архива по метаданным официального выпуска Adoptium на GitHub; файлы распаковываются с проверкой путей, а версия проверяется запуском `java -version`. При повторном запуске проверенная копия используется без повторной загрузки. Загрузка зависит от доступности GitHub и его CDN. Для других платформ и версий пока сохраняется прежний механизм Mojang.
