# Защита репозитория: rulesets

Правила лежат в git, а не только в веб-интерфейсе: их видно в диффе, они
рецензируются как код, и после случайного удаления их можно восстановить.

Два ruleset-а отвечают на два разных вопроса:

| Файл | Вопрос | Ответ |
| --- | --- | --- |
| `main.json` | Как что-то попадает в `main`? | Только через PR, с линейной историей, без удаления и без force-push |
| `workflows.json` | Кто может менять сам CI? | Никто, кроме администраторов репозитория |

## Что именно запрещает `main.json`

`bypass_actors: []` — **пусто, и это главное**. Если администратор в списке
обхода, он может смёржить свой PR в одиночку, не дожидаясь проверок; тогда всё
остальное — декорация. Пустой список означает, что правило действует и на
владельца тоже.

| Правило | Что делает |
| --- | --- |
| `deletion` | `main` нельзя удалить |
| `non_fast_forward` | force-push запрещён: историю нельзя переписать |
| `update` | пушить прямо в `main` нельзя вообще — только через PR |
| `required_linear_history` | в `main` не бывает merge-коммитов, история читается сверху вниз |
| `pull_request` | изменения попадают только PR-ом |
| `required_status_checks` | PR не смёржится, пока не зелены четыре проверки |

### Почему `required_approving_review_count: 0`

Это сольный репозиторий. При `1` GitHub требует, чтобы PR кто-то одобрил, а
одобрить собственный PR нельзя — мёрж встаёт навсегда, ровно как это случилось
с PR #85. Ноль одобрений при этом не ослабляет защиту: пушить в `main` напрямую
всё равно нельзя, а смёржить PR может только тот, у кого есть право записи, —
сейчас это один аккаунт.

Если в проекте появится второй человек, правильное изменение — поставить `1`,
а не полагаться на то, что «и так никто не смёржит».

### Почему `require_extra_approval_for_unattributed_changes: false`

Этот флаг требует **дополнительное** одобрение, если в PR есть коммит, который
GitHub не может привязать к аккаунту. Коммиты агента несут трейлер
`Co-authored-by`, и GitHub трактует такие PR как неатрибутированные. С
`true` (значение по умолчанию) каждый PR агента требует ручного Approve —
именно это заблокировало #85.

Для сольного репозитория с одним аккаунтом он не даёт ничего: одобрять всё
равно некому, кроме автора, а автор себя одобрить не может.

### Обязательные проверки

Выбраны четыре из одиннадцати — те, что быстрые и не зависят от сети:

- `rust-pure` — чистая логика Rust;
- `secret-scan` — gitleaks;
- `frontend (ubuntu-latest)` и `frontend (windows-latest)` — тесты и сборка.

`rust (…)` намеренно **не** в списке: три этих джоба красные из-за
отсутствующего в `Cargo.lock` пакета `mc-launcher-core`. Пока это не починено,
включение их в обязательные заблокирует любой мёрж. **После починки lockfile
их нужно добавить** — иначе сломанный Rust сможет попасть в `main`.

`strict_required_status_checks_policy: true` требует, чтобы проверки были
зелёными на **последнем** коммите ветки, а не на каком-то из прошлых.

## Что запрещает `workflows.json`

`file_path_restriction` на `.github/workflows/**` и `.github/rulesets/**`:
изменить CI или эти самые правила нельзя никаким пушем, кроме администратора.

Без этого правила защита обходится в два шага: сначала PR, который ослабляет
`ci.yml`, потом любой PR, который проходит уже ослабленные проверки.

У этого ruleset-а `bypass_actors` **не** пустой: администратор должен иметь
возможность починить сломанный CI. Владелец и так единственный, кто может
пушить в `main`.

## Как применить

Нужен токен с правом `administration`. У токена агента его нет — `POST
/rulesets` отвечает `403 Resource not accessible by integration`, поэтому
применяет владелец.

```bash
# Создать (первый раз; отвечает 201 и печатает новый id)
gh api --method POST repos/ilya-lavrov68/Line-Launcher/rulesets \
  --input .github/rulesets/main.json
gh api --method POST repos/ilya-lavrov68/Line-Launcher/rulesets \
  --input .github/rulesets/workflows.json

# Обновить (когда файл поменяли)
ID=$(gh api repos/ilya-lavrov68/Line-Launcher/rulesets \
  --jq '.[] | select(.name == "main") | .id')
gh api --method PUT "repos/ilya-lavrov68/Line-Launcher/rulesets/$ID" \
  --input .github/rulesets/main.json

# Проверить, что вышло
gh api repos/ilya-lavrov68/Line-Launcher/rules/branches/main \
  --jq '.[] | .type'
```

Если `gh` не авторизован с нужными правами, то же самое руками:
**Settings → Rules → New ruleset → Import a ruleset** и выбрать файл.

## Что это не закрывает

Честно, чтобы не создавать ложного ощущения защиты:

- **Форки.** Публичный репозиторий можно форкнуть, и запретить это нельзя.
  Форк не влияет на `main`, но и «никто не подгрузит сюда» — про `main`, а не
  про интернет.
- **Внешние PR.** Кто угодно может открыть PR; смёржить его может только
  владелец, а обязательные проверки выполняются на коде PR. Секретов PR из
  форков не получает.
- **Утечка токена владельца.** Правило `bypass_actors: []` не защищает от
  того, у кого на руках окажется токен с правом записи. Это закрывается
  двухфакторной аутентификацией и короткоживущими токенами, а не ruleset-ом.
- **Зависимости.** `package-lock.json` и `Cargo.lock` не защищены: их меняют
  `npm ci` и `cargo`. Если нужно, добавьте их в `restricted_file_paths`.
