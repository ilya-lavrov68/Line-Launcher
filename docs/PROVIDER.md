# Контракт провайдера Line Launcher v1

Провайдер размещает UTF-8 JSON на HTTPS. **Адрес этого документа задаётся на этапе сборки** в `branding/provider.json` — игрок его не вводит и не выбирает провайдера. Провайдер всегда один, а все его серверы перечисляются в этом конфиге. Конфигурация и дистрибутив находятся под контролем провайдера; лаунчер не предоставляет централизованный каталог серверов.

Быстрая сборка своего лаунчера — [START.md](START.md).

Полная типизация: `src/types/line.ts`. Серверная проверка: `src-tauri/src/line/config.rs`. Рабочий структурный пример: `examples/config.json` (его URL, размеры и нулевой хеш — заглушки, не реальный дистрибутив).

## Конфигурация

JSON использует `snake_case`; IPC Tauri — `camelCase`.

| Поле                     | Требование                                                                                                                                                                        |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schema_version`         | Сейчас ровно `1`                                                                                                                                                                  |
| `min_launcher_version`   | Строгий SemVer, например `0.1.0`                                                                                                                                                  |
| `provider.id`            | Lowercase ASCII slug, до 64 символов                                                                                                                                              |
| `provider.name`          | Непустое название, до 100 символов                                                                                                                                                |
| `provider.logo_url`      | Необязательный HTTPS URL                                                                                                                                                          |
| `provider.auth`          | Обязательный объект: `login_url` (HTTPS) и необязательный `register_url`. Один аккаунт на весь проект                                                                             |
| `provider.wardrobe`      | Необязательный объект; требует **оба** поля `skin_url` и `skin_upload_url`, оба HTTPS. Гардероб общий для аккаунта                                                                |
| `anticheat`              | Необязательный объект: `scan_resourcepacks`, `extra_keywords`, `allow`. По умолчанию проверка включена. [ANTICHEAT.md](ANTICHEAT.md)                                              |
| `provider.support_email` | Необязательный адрес почты поддержки проекта. Показывает игроку кнопку «Связаться с провайдером» в настройках; письмо открывается черновиком с диагностикой. Только адрес, не URL |
| `cache_ttl_seconds`      | Необязательный, 60–86400; по умолчанию 300                                                                                                                                        |
| `required_features`      | Поддерживаются `custom-auth-v1`, `zip-sha256-v1`, `launch-manifest-v1`, `private-ipc-v1`, `skin-upload-v1`; неизвестные возможности запрещены                                     |
| `servers`                | 1–100 записей с уникальными `id`                                                                                                                                                  |

Сервер содержит `id`, `name`, `description`, `version`, необязательные `icon_url`, `banner_url`, `minecraft_version` и `auth`. Для ZIP укажите `distribution`; экспериментальные сборки из packwiz/Modrinth описаны в [SOURCES.md](SOURCES.md).

Аккаунт и гардероб живут на `provider`, а не на сервере: игрок входит один раз и
получает доступ ко всем серверам конфига. У сервера остаётся только необязательный
`auth` с эндпоинтами запуска (`launch_ticket_url` + `session_exchange_url`, задаются
только парой). Полей `server.auth.login_url` и `server.wardrobe` в схеме больше нет —
конфиг с ними будет отклонён с понятной ошибкой.

Каждый объект сервера задаёт собственное оформление и дистрибутив. Игрок может
смотреть каталог сеткой карточек или компактным списком «Гармонь»; вид не меняет
содержимое и порядок `servers`. Массив принимает до 100 записей, поэтому один
конфиг провайдера может описать весь каталог.

| Поле         | Требование                                                                                               |
| ------------ | -------------------------------------------------------------------------------------------------------- |
| `icon_url`   | Необязательный HTTPS URL квадратной иконки сервера (рекомендуется 128×128 и больше)                      |
| `banner_url` | Необязательный HTTPS URL широкого баннера (рекомендуется 1600×400, соотношение около 4:1)                |
| `auth`       | Необязательный объект только для запуска: `launch_ticket_url` и `session_exchange_url` вместе, оба HTTPS |

`logo_url` у сервера — устаревшее имя `icon_url`. Лаунчер читает его как алиас,
чтобы существующие конфиги не сломались, но новые конфиги должны использовать
`icon_url`. `provider.logo_url` не менялся.

Изображения загружаются напрямую WebView по HTTPS. Отсутствующая или недоступная
картинка не ломает интерфейс: карточка показывает знак-заглушку, баннер
скрывается. Ссылки должны быть публично доступными и отдавать корректный
`Content-Type`; для предпросмотра скина с другого origin нужен
`Access-Control-Allow-Origin` (canvas читает пиксели).

`distribution` требует **одно** поле:

- `url`: HTTPS-адрес ZIP. Больше ничего заполнять не нужно.

Три поля ниже необязательны. Указали — значение проверяется побайтно; не
указали — лаунчер измеряет архив во время скачивания и использует измеренное:

- `sha256`: 64 lowercase hex символа полного ZIP;
- `size_bytes`: размер ZIP, 1 байт–4 ГиБ;
- `unpacked_size_bytes`: сумма размеров обычных файлов, 1 байт–16 ГиБ; служебный marker лаунчера не входит.

**Новая сборка** — это новый ZIP и поднятый `version` у сервера. Адрес можно
оставить тем же: отпечаток изменится, и лаунчер скачает архив заново. Если
адрес неизменяемый и архив по нему никогда не меняется (рекомендуется), при
каждом релизе меняйте ещё и `url`.

Порядок выпуска без ручных хешей:

```sh
npm run pack:manifest release.zip https://cdn.example.com/release.zip
# рядом с архивом появится pack.json с sha256 и размерами
```

Положите `pack.json` рядом с архивом и укажите серверу `pack_manifest_url` —
тогда `config.json` вообще не нужно трогать на каждый релиз. Если предпочитаете
одну ссылку совсем без `pack.json`, оставьте `distribution: { "url": … }`:
отпечаток возьмётся из скачанного архива.

> Первое скачивание по голой ссылке доверяет HTTPS и вашему серверу — сверять
> пока не с чем. Дальше отпечаток хранится в квитанции установки и используется
> при запуске, обновлении и откате. Если сервер сборки может быть
> скомпрометирован, укажите `sha256` явно — подмена архива тогда не пройдёт.

Поддерживаются ZIP Stored/Deflate без шифрования, symlink и специальных файлов; до 50 000 записей. Не включайте пользовательские миры/настройки в архив, который должен обновляться поверх пользовательских данных: текущая модель устанавливает независимые релизы, overlay-политика будет отдельным контрактом.

## Авторизация

`provider.auth.login_url` обязателен, `provider.auth.register_url` необязателен. Отсутствие register URL скрывает регистрацию. Оба endpoint принимают POST JSON только напрямую по HTTPS; redirects намеренно не выполняются.

Вход выполняется **один раз при запуске лаунчера**, до выбора сервера. Сессия одна на весь проект: она открывает все серверы конфига и общий гардероб. Выход из аккаунта закрывает доступ сразу ко всем серверам. Сессия сбрасывается только при смене адреса конфига, `provider.id` или `provider.auth` — изменение списка серверов или их дистрибутивов вход не сбрасывает.

Запрос:

```json
{
  "username": "Player_name",
  "password": "password-from-form"
}
```

`server_id` в запросе входа больше нет: аккаунт не привязан к серверу.

Успешный ответ HTTP 200:

```json
{
  "access_token": "provider-session-token",
  "expires_in": 3600,
  "username": "Player_name"
}
```

`access_token` обязателен; `expires_in` — секунды, 1–86400; `username` необязателен. Ответ ограничен 16 КиБ. Не возвращайте пароль. Не логируйте request/response на стороне провайдера. Rate limiting, проверка паролей, блокировки и отзыв сессий — ответственность API провайдера.

Ошибки: 401/403 — отказ авторизации; 409 — логин занят; 429 — rate limit; 5xx — временная недоступность. Тело ошибки не показывается игроку и не должно содержать секретов.

Токен не возвращается frontend. Обмен launch ticket использует отдельный одноразовый короткоживущий credential; долгоживущий `access_token` не предназначен для JVM-аргументов.

## Запуск игры и одноразовый ticket

Для включения запуска сервер должен задать **оба** поля `auth.launch_ticket_url` и
`auth.session_exchange_url` (HTTPS, без redirect для ticket endpoint). Дистрибутив
должен содержать `line-launch.json` у корня ZIP; пример — `examples/line-launch.json`.

Манифест сборки:

```json
{
  "schema_version": 1,
  "java_major": 21,
  "main_class": "net.minecraft.client.main.Main",
  "classpath": ["client.jar", "libraries/example.jar"],
  "minecraft_version": "1.21.1",
  "asset_index": "21",
  "assets_dir": "assets",
  "natives_dir": "natives",
  "logging_config": "log4j2.xml",
  "game_args": ["--launchTarget", "forgeclient"],
  "user_type": "mojang"
}
```

`launch_mode` у сервера необязателен: по умолчанию `ticket`. Для локальной
офлайн-сборки задайте `"launch_mode": "offline"` и не задавайте пару ticket/exchange;
добавьте `offline-launch-v1` в `required_features`. Отсутствие endpoints само по
себе оставляет запуск выключенным. Подробнее — [GAME.md](GAME.md).

### Режим `minecraft`

`"launch_mode": "minecraft"` — сервер, на который лаунчер ставит **настоящий
клиент Minecraft** (ваниль или Fabric/Forge/NeoForge через `mc-launcher-core`) и
заходит без главного меню. Это единственный режим, который ходит к Mojang, и он
включается **только явно**:

```json
{
  "id": "survival",
  "name": "Survival",
  "description": "Классическое выживание.",
  "version": "2026.11.1",
  "minecraft_version": "1.21.1",
  "launch_mode": "minecraft",
  "server_address": "play.example.com:25565",
  "distribution": {
    "url": "",
    "url": "https://cdn.example.com/release.zip"
  }
}
```

- `server_address` и `minecraft_version` **обязательны**: лаунчер отклонит конфиг
  при разборе, а не оставит кнопку, которая не работает. Адрес принимает `host`,
  `host:port` и `[ipv6]:port`; порт по умолчанию 25565.
- `distribution` не используется: режим ставит клиент из манифестов Mojang, а не
  из архива провайдера, поэтому пустая заглушка допустима (во всех остальных
  режимах `url` обязателен, а заявленные дополнительно размеры и хеш
  проверяются).
- `launch_ticket_url`/`session_exchange_url` задавать нельзя: вход идёт под ником
  аккаунта проекта (офлайн-идентичность), без билета и без обмена сессии.
- Сервер должен работать с `online-mode=false`. Лаунчер не подделывает сессию
  Mojang и не пытается обойти `online-mode=true` — такой сервер просто не пустит.

Лаунчер показывает этот режим отдельной панелью на странице сервера; у серверов с
другим `launch_mode` он не появляется вообще. Подробности и ограничения —
[MINECRAFT.md](MINECRAFT.md).

`logging_config`, `game_args` и `user_type` необязательны. `logging_config` —
обычный файл внутри релиза, попадает в `-Dlog4j.configurationFile`. `game_args` —
дополнительные **игровые** аргументы строго парами `--имя значение` (не больше 128,
без дубликатов, значение не начинается с `-`); переопределять `--gameDir`,
`--username`, `--uuid`, `--accessToken`, `--userType`, `--version`,
`--versionType`, `--assetIndex`, `--assetsDir`, `--session`, `--userproperties` и
ключи JVM (`-X`/`-XX`, `--add-opens`, `--patch-module`, …) нельзя. `user_type` —
`mojang` (по умолчанию), `msa` или `legacy`.

Поля строго проверяются. Запрещены неизвестные поля, абсолютные пути, `..`,
symlink, classpath-каталоги/glob и произвольные JVM-аргументы. `asset_index` и
`assets_dir` задаются только вместе. Java ищется локально (`JAVA_HOME`, `PATH`,
стандартные каталоги ОС) или выбирается игроком вручную и проверяется запуском
`java -version`; требуется точное совпадение `java_major`.

`--gameDir` указывает на отдельный каталог экземпляра (`instances/<id>/game`), а
не на распакованный релиз: миры и настройки игрока не теряются при обновлении и
восстановлении сборки. Сейчас клиент получает legacy `--uuid`, вычисленный из
имени; он нужен для стабильности локальных игровых данных, но не подтверждает
личность и не должен самостоятельно связывать аккаунт проекта. Выбранное
направление — первая серверная привязка UUID модом после подтверждённого входа
по одноразовому launch-ticket; интерфейс лаунчера UUID не отправляет. До
согласования протокола мода это не считать реализованной возможностью.
`--accessToken 0` — заглушка: настоящий ticket идёт только по приватному каналу.
Подробный разбор команды — в [GAME.md](GAME.md).

Launcher POST-ит на `launch_ticket_url` с заголовком
`Authorization: Bearer <provider access_token>`:

```json
{
  "server_id": "survival",
  "sha256": "<хеш установленного релиза>",
  "channel_id": "<uuid приватного канала>",
  "username": "Player_name"
}
```

Ответ HTTP 200:

```json
{ "ticket": "one-shot-ticket", "expires_in": 60 }
```

`expires_in` — 1–120 секунд. Ticket должен быть привязан к серверу, релизу,
каналу и пользователю, использоваться один раз и истекать на стороне провайдера.
Launcher передаёт ticket моду только через приватный IPC: Unix socket
`/tmp/line-ipc-<uuid>/ticket.sock` (каталог `0700`, socket `0600`) или Windows
named pipe `\\.\pipe\line-launcher-<uuid>` с ACL текущего пользователя. Listener
создаётся до spawn Java; проверяется PID/UID дочернего процесса. JVM получает
лишь `-DlineLauncher.sessionChannel=<uuid>`. Весь обмен ограничен одним deadline
(не более 60 с и не более `expires_in`), сообщение — 16 КиБ.

Мод отправляет в канал одну строку JSON:

```json
{ "type": "line.launch-ticket.request", "channel": "<uuid>" }
```

Launcher отвечает одной строкой:

```json
{
  "type": "line.launch-ticket.response",
  "ticket": "one-shot-ticket",
  "exchange_url": "https://auth.example.com/v1/launcher/exchange",
  "server_id": "survival",
  "sha256": "<хеш релиза>",
  "username": "Player_name"
}
```

Мод немедленно POST-ит на `exchange_url` без redirect:

```json
{
  "ticket": "one-shot-ticket",
  "server_id": "survival",
  "sha256": "<хеш релиза>",
  "channel_id": "<uuid приватного канала>",
  "username": "Player_name"
}
```

Формат успешного ответа обмена — ответственность провайдера и мода (игровая
сессия/Minecraft profile). Повторное использование, истечение и несоответствие
любой привязки (`server_id`, `sha256`, `channel_id`, `username`) должны
отклоняться сервером. Справочный Java-клиент канала находится в
`examples/mod-client/LineTicketClient.java`: строгий flat-JSON codec, HTTPS без
redirect, таймауты и лимиты размера. Интеграция с конкретным mod loader остаётся
на стороне провайдера. Не логируйте ticket и не передавайте его через аргументы
JVM. Воспроизводимый интеграционный тест клиента против локального HTTPS
provider stub и IPC peer: `npm run test:java` (требуется JDK 17+; CI запускает его
на Linux/Windows/macOS).

## Целостность установленной сборки

При распаковке лаунчер считает sha256 каждого файла и кладёт рядом с релизом
`.line-files.json`; маркер `.line-complete` пишется только после индекса. Архив,
содержащий `.line-files.json` или `.line-complete`, отклоняется как небезопасный.

Перед каждым запуском весь релиз сверяется с индексом:

- посторонние файлы (которых нет в индексе) удаляются, опустевшие каталоги
  подчищаются;
- изменённые или отсутствующие файлы приводят к повторному скачиванию и
  распаковке архива с тем же sha256, после чего проверка выполняется снова;
- отсутствие индекса, symlink или специальный файл внутри релиза — тоже полное
  восстановление; по ссылке лаунчер ничего не читает;
- если сразу после восстановления файлы снова отличаются, запуск отменяется с
  ошибкой `INTEGRITY`.

Провайдеру ничего дополнительно делать не нужно: политика применяется к тому, что
объявлено в `distribution`. Пользовательские файлы в каталоге релиза не
предусмотрены — данные игрока живут в `instances/<id>/game`. Детали и примеры —
в [GAME.md](GAME.md).

## Проверка сборки перед запуском

Лаунчер сверяет файлы сборки при каждом запуске и проверяет ресурс-паки в
`game/` на ключевые слова. По умолчанию всё включено — ничего настраивать не
нужно, а старый конфиг без блока `anticheat` ведёт себя так же, как новый с ним.

```jsonc
"anticheat": {
  "scan_resourcepacks": true,
  "extra_keywords": ["mymod-xray"],
  "allow": ["<sha256 пака>"]
}
```

- `extra_keywords` **добавляет** слова к встроенному списку. Убрать встроенное
  слово нельзя: список меняется только через код.
- `allow` — sha256, а не имя файла: исключение по имени обходится
  переименованием.
- `scan_resourcepacks: false` выключает только поиск слов. Проверка посторонних
  файлов в `resourcepacks/` остаётся: она не про слова, а про «этого файла никто
  не публиковал».

Подробности, включая то, чего проверка не делает: [ANTICHEAT.md](ANTICHEAT.md).

## Поддержка

`provider.support_email` — необязательное поле, которое не влияет на работу
лаунчера, но влияет на разговор с игроком. Если оно задано, в настройках
появляется кнопка **«Связаться с провайдером»**: черновик письма на этот адрес
с уже вставленным отчётом диагностики (версия, ОС, провайдер, состояние сессии,
последние 400 строк логов лаунчера). Паролей и токенов в отчёте нет — см.
[LOGGING.md](LOGGING.md).

Проверяется как адрес почты, а не как ссылка: `mailto:` собирает сам лаунчер,
поэтому `?`, `#`, `&`, пробелы и вторая `@` отклоняются при валидации конфига.

Учтите разделение: это адрес **провайдера**. Адрес издателя сборки лежит в
`branding/owner.ts` и через `config.json` не настраивается — иначе перекрасивший
сборку перенаправил бы себе диагностику всех игроков.

## Гардероб (скины)

Гардероб включается объектом `provider.wardrobe` и обязательной feature
`skin-upload-v1` в `required_features`. Он общий для аккаунта: одна текстура на все
серверы проекта, поэтому хранить скины нужно по игроку, а не по серверу. Без
объекта `provider.wardrobe` вкладка «Гардероб» остаётся полностью рабочей, но
локальной — лаунчер объясняет, что проект не настроил гардероб. Все запросы идут с
`Authorization: Bearer <access_token>` единственной сессии проекта; при `401`/`403`
лаунчер требует повторный вход.

Отправка автоматическая: лаунчер сам пушит активный скин при выборе текстуры,
входе и открытии гардероба. Кнопки «Отправить на сервер» нет. Отправка
идемпотентна — лаунчер хранит отметку «что провайдер уже принял» и не шлёт повторно
неизменившийся скин; отметка пишется только после успешного ответа, поэтому
неудачная отправка повторяется сама. Выбор «Стандартный скин» отправляет `DELETE`.
Повторные и параллельные вызовы безопасны.

| Метод    | Endpoint          | Тело запроса                                                                   | Ответ                                                                                 |
| -------- | ----------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| `GET`    | `skin_url`        | —                                                                              | `200 {"model":"classic"\|"slim","texture_url":"https://…"}` или `404`, если скина нет |
| `POST`   | `skin_upload_url` | Сырые байты PNG, `Content-Type: image/png`, `X-Skin-Model: classic` или `slim` | Тот же JSON, что и у `GET`                                                            |
| `DELETE` | `skin_upload_url` | —                                                                              | `204` (или `200`) — вернуть стандартный скин                                          |

Ответ лаунчер читает с лимитом 16 КиБ и требует HTTPS для `texture_url`.
Ограничения на файл проверяются **и в лаунчере, и на стороне провайдера** — не
доверяйте клиенту:

- не более 256 КиБ;
- корректная сигнатура PNG и `IHDR` длиной 13;
- размер ровно `64×64` или `64×32` (legacy-формат до 1.8);
- глубина 8 бит, цветовой тип 2 (RGB) или 6 (RGBA), без чересстрочной развёртки.

Провайдер сам решает, куда положить текстуру (Mojang-совместимое хранилище,
собственный CDN, БД) и как применить её в игре. Лаунчер только передаёт файл и
модель и показывает результат. Reference-реализация всех трёх методов —
`examples/provider/server.mjs`.

При превышении лимита отвечайте `413`, а не обрывом соединения: иначе игрок
увидит общую сетевую ошибку вместо понятной причины. Текстура должна отдаваться с
`Access-Control-Allow-Origin`, иначе canvas не сможет построить предпросмотр.

`npm run test:wardrobe` проверяет этот контракт целиком по настоящему HTTPS:
отказ без сессии и с чужим токеном, `404` без скина, отказ без/с неизвестной
моделью, неверный `Content-Type`, отсутствие сигнатуры PNG, неверный размер,
`413` на большом теле, приём `64×64` slim и legacy `64×32`, чтение и скачивание
текстуры, сброс и отсутствие токена в логах. JDK не требуется.

## Серверный профиль: API пока не подключён

Для статистики по выбранному серверу и достижений выбран единый endpoint,
ориентировочно `GET /launcher/servers/{server_id}/profile`, с авторизацией
существующей сессией. Это пока направление, а не публичный wire-контракт:
точная схема ответа, пустое состояние и правила ошибок не утверждены. Лаунчер
не вызывает endpoint и не показывает демонстрационные счётчики.

Для будущего профиля нужны счётчики блоков, убитых мобов, убитых игроков и
смертей, ванильные Minecraft Advancements и достижения модов отдельными
группами. Фракционный раздел включается явным флагом конфигурации сервера;
имя/тип флага ещё не согласованы. Данные фракций предоставляет серверный мод,
не вычисляет лаунчер. Требования к карточке: название группы, роль игрока,
число участков — без списка участников. Схему и критерии подключения ведём в
[ROADMAP.md](ROADMAP.md); до согласования никаких endpoint или полей не
придумывать.

## Конфигурация и кэш

- Каждый redirect проверяется; URL с username/password и fragment запрещены.
- Конфиг ограничен 1 МиБ.
- Ответ 304 используется только при наличии сохранённого валидного конфига.
- При сетевой ошибке показывается старый конфиг с отметкой stale; вход/установка через stale-конфигу в UI заблокированы.
- Новая схема, неизвестная обязательная feature, невалидный JSON/хеш не заменяются старым кэшем.
- Сервер должен отдавать корректный `Content-Type: application/json`; лаунчер валидирует содержимое независимо от MIME.

## Откат и хранение релизов

Launcher ведёт `history.json` и позволяет явно откатить `current.json` на ранее
установленный полный релиз. По умолчанию хранятся текущий релиз и два самых
недавних других; запущенный релиз дополнительно защищён от удаления. Установка,
откат, очистка и весь жизненный цикл запущенной игры выполняются под одним
cross-process lock: другой процесс лаунчера не может удалить живой релиз.
Во время запуска/игры установка/откат/смена конфигурации и выход из аккаунта
блокируются. Повторная установка уже опубликованного релиза восстанавливает
`history.json` и retention после сбоя между атомарными записями.

## Референсная реализация провайдера

`examples/provider/` содержит **одноразовый протокол целиком** в development-виде:
`server.mjs` (config/login/register/ticket/exchange/skin с ETag, replay/expiry/binding
отказами), `build-pack.mjs` (реальный ZIP с `line-launch.json` и `client.jar`) и
`DemoGame.java` (main class, который выполняет handshake и завершается).

```sh
npm run provider:pack
npm run provider:serve
npm run test:provider
# Только контракт гардероба, по настоящему HTTPS и без JDK:
npm run test:wardrobe
```

Это **не** production-код: аккаунты и ticket в памяти, пароль проверяется demo-сравнением,
сертификат самоподписанный. Используйте его как исполняемую спецификацию и как
контрагент для ручной проверки настольного приложения (`docs/RUNBOOK.md`).

## Границы контракта и режимы запуска

Не путайте два пути. Описанный выше провайдерский запуск с `game_args` не
принимает произвольные `jvm_args` и сам по себе не обеспечивает полноценный
запуск Forge/NeoForge и докачку Minecraft. Для `launch_mode: "minecraft"`
используется отдельный путь через `mc-launcher-core`: он может подготовить
клиент, библиотеки, ресурсы и загрузчик, но поддержка отдельных версий требует
проверки на реальных экземплярах. Для ZIP дополнительная подготовка требует
согласия; оно пока не является точным списком всех загрузок. См.
[MINECRAFT.md](MINECRAFT.md) и [INSTALLATION-AUDIT.md](INSTALLATION-AUDIT.md).

Лаунчер обнаруживает установленную Java и в предусмотренных путях может предложить
автоматическую установку; на Windows x64 есть загрузка Temurin. Отдельное
согласие на Java реализовано для ZIP `mc_play`, но не доказано для всех прямых
команд и сторонних установщиков. Конфиг провайдера не задаёт путь Java игрока,
heap или произвольные JVM-флаги. Microsoft-авторизация не поддерживается;
интеграция мода с сессией и проверка одноразового ticket остаются за провайдером.
Подпись конфигурации и политика пользовательских файлов требуют отдельной работы.
