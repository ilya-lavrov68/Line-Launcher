# Ранбук: что нужно сделать вне песочницы

Этот документ — пошаговая инструкция для действий, которые **нельзя выполнить в
среде разработки агента**: полная сборка Rust, проверки на Windows/macOS,
реальный запуск Minecraft, подпись кода и публикация обновлений.

Каждый раздел содержит: зачем это нужно → что сделать → как понять, что получилось
→ что делать, если не получилось.

Нужна короткая инструкция, а не полный разбор? Начните с [START.md](START.md).
Совсем с нуля, «что ставить и какой файл править» — [BUILD.md](BUILD.md).

Текущий фактический статус проверок — в [VERIFICATION.md](VERIFICATION.md).
Контракт провайдера — в [PROVIDER.md](PROVIDER.md).

**Linux (Debian/Ubuntu):**

### 1.2. Установка проекта

```sh
git clone <ваш-репозиторий> Line-Launcher
cd Line-Launcher
npm ci
npm run doctor       # проверяет всё окружение и печатает, чего не хватает
```

**Готово, если:** `npm run doctor` завершился с кодом 0 и напечатал «Готово к сборке».

`npm run tauri dev` и `npm run tauri:build` запускают эту проверку автоматически,
поэтому вместо невнятного `cargo metadata ... program not found` вы сразу
увидите, чего именно не хватает.

### 1.3. Если `tauri dev` пишет `cargo metadata: program not found`

Это значит, что **Rust не установлен** (или не попал в `PATH`). Сам лаунчер тут
ни при чём: Tauri вызывает `cargo`, а его нет в системе.

**Windows**

1. Установите Rust: скачайте <https://win.rustup.rs/x86_64>, запустите, выберите
   вариант `1) Proceed with standard installation`.
2. Установите **Microsoft C++ Build Tools**:
   <https://visualstudio.microsoft.com/visual-cpp-build-tools/> → workload
   «Разработка классических приложений на C++», обязательно с компонентом
   «Windows 10/11 SDK». Без него Rust установится, но линковка упадёт на
   `link.exe`.
3. Убедитесь, что установлен **WebView2 Runtime** (в Windows 11 он уже есть):
   <https://developer.microsoft.com/microsoft-edge/webview2/>
4. **Закройте и заново откройте терминал** — `PATH` подхватывается только при
   старте процесса. Это самая частая причина «я же установил, а не работает».
5. Проверьте: `rustc --version`, `cargo --version`, затем `npm run doctor`.

**macOS:** `xcode-select --install`, затем
`curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh`.

**Linux:** та же команда `rustup` плюс системные пакеты из раздела 1.1.

Первый `npm run tauri dev` после установки собирает ~470 крейтов и занимает
несколько минут — это нормально, последующие запуски быстрые.

### 1.4. Если doctor говорит «MSVC не установлен», а он установлен

Проверка ищет toolchain тремя способами: через `vswhere`, по наличию `cl.exe` на
диске и — если первые два не нашли — реальной пробной линковкой через `rustc`.
Пробная компиляция решает спор: если она прошла, doctor считает окружение годным,
даже когда Visual Studio стоит на нестандартном диске.

Проверить вручную:

```powershell
& "${env:ProgramFiles(x86)}\Microsoft Visual Studio\Installer\vswhere.exe" `
  -latest -products * -requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64 `
  -property installationPath
```

Пустой вывод означает, что компонент C++ действительно не выбран в инсталляторе
(сам Visual Studio при этом может быть установлен). Откройте Visual Studio
Installer → «Изменить» → вкладка «Отдельные компоненты» → отметьте
«MSVC v143 — VS 2022 C++ x64/x86 build tools» и «Windows 11 SDK».

Если проверка ошибается, а сборка при этом идёт, её можно пропустить:

```powershell
$env:LINE_SKIP_DOCTOR=1; npm run tauri dev
```

### 1.5. Если doctor говорит «WebView2 не найден», а окно открывается

Проверка искала `msedgewebview2.exe` прямо в `…\Microsoft\EdgeWebView\Application`,
но Evergreen-рантайм кладёт его **в подпапку версии**:
`…\EdgeWebView\Application\<версия>\msedgewebview2.exe`. Такой путь не существовал
никогда, поэтому doctor всегда писал «не найден» — даже там, где рантайм стоит.
На Windows 11 он предустановлен.

**Исправлено.** Теперь основной источник — реестр (правило Microsoft), значение
`pv` в ключе `{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}`:

```powershell
reg query "HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}" /v pv
reg query "HKCU\Software\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}" /v pv
```

Версия больше `0.0.0.0` — рантайм установлен. Ключ может существовать с
`pv = 0.0.0.0`, и это значит «не установлен»; такое значение не считается.
Doctor печатает найденную версию и источник: `147.0.3912.98 [registry]`.

Если предупреждение осталось и обе команды ничего не нашли — рантайма действительно нет,
поставьте Evergreen Standalone: https://developer.microsoft.com/microsoft-edge/webview2/

### 1.6. Если `npm run dev` падает на `spawnSync npx.cmd EINVAL`

Начиная с Node 18.20.2 / 20.12.2 (исправление CVE-2024-27980) запуск `.cmd`-файла
без шелла запрещён. Генератор брендинга запускал `npx.cmd` для `tauri icon` —
теперь он вызывает JS-точку входа CLI напрямую через текущий Node, поэтому
ошибка больше не возникает.

Заодно устранена причина, по которой иконки перегенерировались **при каждом**
запуске: Git for Windows по умолчанию ставит `core.autocrlf=true`, штамп
`src-tauri/icons/.brand-source.sha256` читался как CRLF и никогда не совпадал.
В репозитории появился `.gitattributes` (`* text=auto eol=lf`), а сравнение
файлов игнорирует различия в переводах строк.

Если вы клонировали репозиторий до этого исправления, нормализуйте окончания
строк один раз:

```powershell
git add --renormalize .
git status        # должны быть только ожидаемые изменения
```

### 1.7. Если Tauri пишет `Found version mismatched Tauri packages`

Tauri требует, чтобы крейт `tauri` (версия из `src-tauri/Cargo.lock`) и npm-пакет
`@tauri-apps/api` совпадали **по major и minor**. Патч-версии могут различаться.

```sh
npm run check:tauri     # показывает обе версии и точную команду для выравнивания
```

Обычно отстаёт npm: крейт был задан как `version = "2"` и уплывал на самый свежий
minor, пока `package-lock.json` держал старый. Теперь обе стороны закреплены на
minor (`~2.12` в Cargo.toml, `~2.12.x` в package.json) и обновляются только вместе:

```sh
npm install @tauri-apps/api@~2.13 @tauri-apps/cli@~2.13
# и в src-tauri/Cargo.toml: tauri = { version = "~2.13", ... }
cargo update -p tauri
```

Проверка встроена в `npm run doctor` и в CI, поэтому рассинхрон больше не
обрывает сборку на середине.

### 1.8. Если `provider:serve` пишет `spawnSync openssl ENOENT`

openssl нужен только для самоподписанного сертификата демо-провайдера. Отдельная
установка обычно не требуется: **Git for Windows уже содержит рабочий openssl** в
`<Git>\usr\bin\openssl.exe`, и скрипты теперь находят его сами (как и варианты
OpenSSL-Win64, Strawberry Perl, MSYS2, Chocolatey). Проверить:

```powershell
& "$env:ProgramFiles\Git\usr\bin\openssl.exe" version
```

Если его действительно нет:

```powershell
winget install --id ShiningLight.OpenSSL.Light
# либо укажите путь явно
$env:LINE_OPENSSL="C:\Program Files\Git\usr\bin\openssl.exe"
```

`npm run doctor` показывает, откуда взят openssl (`[PATH]`, `[Git for Windows]`).

### 1.9. Восстановление Chromium перед screenshot capture

Перед созданием screenshots/GIF обязательно вызовите:

```sh
npm run browser:restore
npm run screenshots
```

`npm run screenshots` также восстанавливает браузер автоматически. Скрипт
проверяет `CHROMIUM_PATH` и системные Chrome/Edge, затем кэш Playwright; если
браузера нет, скачивает закреплённую Chromium-сборку. На Linux x64 при
недоступном CDN Playwright использует совпадающий major из npm registry. Это
не разрешение пропустить проверку: при ошибке восстановления не обновляйте
галерею из старых кадров и разберите вывод скрипта.

Для уже установленного браузера задайте путь:

```powershell
$env:CHROMIUM_PATH="C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe"
npm run browser:restore
npm run screenshots
```

Остальные браузерные smoke-тесты используют ту же переменную `CHROMIUM_PATH`;
их можно запускать после `npm run browser:restore`.

UI-smoke обращается к запущенному dev-серверу, поэтому в другом терминале должен
работать `npm run dev`. Если сервер не поднят, скрипт теперь говорит об этом
прямо, а не падает со стеком соединения.

### 1.10. Про `npm audit`

Число замечаний `npm audit` меняется с зависимостями и базой уязвимостей.
Для отдельной проверки производственных зависимостей используйте:

```sh
npm audit --omit=dev
```

Проверяйте именно эту команду. `npm audit fix --force` применять не нужно —
он ломает мажорные версии инструментов сборки.

### 1.11. Сборка MSI падает с `LGHT0311`

```text
LicenseAgreementDlg.wxs(27) : error LGHT0311 : A string was provided with characters
that are not available in the specified database code page '1252'
```

Rust-приложение собралось — ошибка уже в упаковщике. WiX хранит строки MSI в кодовой
странице языка установщика (`en-US` → 1252), а наш `LICENSE` двуязычный: 4885 символов
кириллицы в 1252 не представимы. Tauri оборачивает текстовую лицензию в RTF с
`\ansicpg1252`, кладя внутрь сырой UTF-8, поэтому байты не совпадают с кодировкой БД.

**Исправлено в репозитории, обновлять ничего не нужно.** MSI и NSIS требуют лицензию
в разном виде, а настройка `bundle.licenseFile` у Tauri одна, поэтому `tauri:build`
делает два прохода:

| Установщик | Лицензия                  | Почему                                                                                           |
| ---------- | ------------------------- | ------------------------------------------------------------------------------------------------ |
| NSIS       | `LICENSE` (обычный UTF-8) | NSIS выводит файл как есть, кириллица работает                                                   |
| MSI        | `src-tauri/LICENSE.rtf`   | ASCII с `\uN`-escape: проходит любую кодовую страницу, а RichEdit всё равно показывает кириллицу |

RTF генерируется из `LICENSE` командой `npm run brand`, переключение делает overlay
`src-tauri/tauri.msi.conf.json`. Бинарник компилируется один раз, второй проход его
переиспользует.

**Готово, если:** в `src-tauri/target/release/bundle/nsis/` и `.../msi/` появились
установщики, а в лицензионном окне **обоих** виден русский текст, а не `\u1056` и не «кракозябры».

**Если не получилось:**

- _В окне MSI вместо текста видны `\rtf1`, `\u1056`._ Значит, в MSI попал обычный
  `LICENSE` вместо RTF — проверьте, что второй проход вызывает `-c src-tauri/tauri.msi.conf.json`.
- _`brand:check` говорит, что файлы устарели._ Запустите `npm run brand`: RTF должен
  соответствовать `LICENSE`. Не правьте `LICENSE.rtf` руками — он генерируемый.
- _Сменили язык установщика на `ru-RU`._ Это не решение: кодовая страница 1251 позволит
  сборке пройти, но RTF всё равно объявляет 1252, и текст отобразится неверно.

## 2. Полная проверка Rust (главный пробел)

В песочнице недоступны архивы крейтов с crates.io, поэтому `cargo check/test/clippy`
не выполнялись. Синтаксис проверен парсером, форматирование — `rustfmt`, а чистая
логика — реальным `rustc`. **Полную компиляцию нужно сделать у вас.**

```sh
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo check --locked --manifest-path src-tauri/Cargo.toml --all-targets
cargo test  --locked --manifest-path src-tauri/Cargo.toml
cargo clippy --locked --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
```

Повторите **на всех трёх ОС** (или доверьте это CI, раздел 8).

**Готово, если:** все четыре команды завершились с кодом 0, `cargo test` показал
`test result: ok` без `failed`, clippy не выдал предупреждений.

**Если не получилось:**

- _Ошибки компиляции._ Наиболее вероятные места — платформенный код:
  `src-tauri/src/line/ipc.rs` (Windows named pipe ACL, `windows-sys`),
  `src-tauri/src/line/java.rs` (поиск JRE), `src-tauri/src/line/launch.rs`
  (монитор процесса). Пришлите текст ошибки — это правится точечно.
- _Clippy ругается на стиль._ Применяйте `cargo clippy --fix` только осознанно;
  подавление через `#[allow(...)]` допустимо с комментарием, почему это безопасно.
- _`cargo test` падает на IPC-тестах._ Они создают реальные сокеты/пайпы; на
  Windows/macOS это первая настоящая проверка ACL и peer-credentials. Не отключайте
  тесты — сообщите об ошибке.
- _Долгая первая сборка._ Tauri собирает 470+ крейтов; 10–20 минут нормально.

## 3. Локальный провайдер и тестовая сборка

Чтобы проверить установку и запуск **без Minecraft и без боевого бэкенда**, в
репозитории есть референсный провайдер и генератор реальной сборки.

> **Простой путь:** `npm run demo` делает всё описанное ниже сам — собирает
> демо-проект, подставляет адрес, запускает провайдера и приложение с локальным
> сертификатом, а при выходе возвращает `branding/provider.json`. Чек-лист
> функций и разбор проблем — [DEMO.md](DEMO.md). Ручные шаги ниже нужны, только
> если вы хотите управлять каждым отдельно.

### 3.1. Собрать пак и запустить провайдер

```sh
npm run provider:pack     # .provider/pack.zip + .provider/config.json
npm run provider:serve    # https://127.0.0.1:8443/config.json
```

Генератор компилирует `DemoGame.java` и справочный `LineTicketClient.java`, кладёт
их в `client.jar`, пишет `line-launch.json` и собирает ZIP. Main class пака
выполняет настоящий обмен ticket по приватному IPC, затем живёт ещё 20 секунд
(`LINE_DEMO_SECONDS`, 0 — сразу выйти), чтобы можно было проверить «Остановить
игру». Проверяется весь путь лаунчера, кроме самого Minecraft.

Генератор собирает **три сервера** (один аккаунт на проект), два релиза Demo
Survival для проверки обновления и отката, оформление и готовые текстуры скинов
в `.provider/skins/`. Без JDK он не падает: собирает устанавливаемые паки и не
публикует эндпоинты запуска, поэтому лаунчер честно показывает «Запуск не
настроен» (`--no-java` делает то же самое принудительно).

Требуется `javac` (JDK 17+) либо `ECJ_JAR` рядом с JRE:

```sh
JAVA_HOME=/path/to/jdk npm run provider:pack
# или
JAVA_HOME=/path/to/jre ECJ_JAR=/path/to/ecj.jar npm run provider:pack
```

Версия Java в манифесте берётся из активного рантайма; переопределить:
`LINE_JAVA_MAJOR=21`.

### 3.2. Довериться самоподписанному сертификату

**Симптом.** Сервер запущен и пишет `Reference provider listening on
https://127.0.0.1:8443`, но лаунчер отвечает «Не удалось проверить сертификат
провайдера» (до версии с этим исправлением — «Не удалось соединиться с
провайдером. Проверьте подключение»).

Это **не сеть**. Провайдер использует самоподписанный сертификат, а лаунчер
намеренно не отключает проверку сертификатов: иначе кто угодно мог бы подменить
ZIP-сборку, которую лаунчер затем запускает. Проверить, что сервер исправен:

```sh
curl https://127.0.0.1:8443/config.json                        # → self-signed certificate
curl --cacert .provider/tls.crt https://127.0.0.1:8443/config.json   # → JSON
```

Если вторая команда отдаёт JSON — сервер в порядке, нужно только доверие.

#### Способ 1 (рекомендуется): доверие только для этого процесса

Не трогает хранилище ОС и не требует администратора. Фича выключена по умолчанию
и компилируется только по явному флагу.

**Windows (PowerShell):**

```powershell
$env:LINE_DEV_CA_CERT = ".provider\tls.crt"
npm run tauri dev -- --features dev-provider-ca
```

**Linux:**

```sh
LINE_DEV_CA_CERT=.provider/tls.crt npm run tauri dev -- --features dev-provider-ca
```

В консоли появится `WARNING: dev-provider-ca active — trusting 1 extra root(s)`.
Публичные корни остаются на месте, проверка сертификатов не отключается —
добавляется ровно один якорь доверия из указанного файла.

> **Никогда не собирайте с этой фичей распространяемый билд.** В `release.yml` она
> не включена, `default = []`. Лаунчер, доверяющий сертификату из working copy,
> позволяет подменить и сборку, и токен авторизации.

**macOS** этот способ не поддерживает (rustls platform verifier не принимает
дополнительные корни) — лаунчер честно скажет об этом. Используйте способ 2.

#### Если лаунчер паникует на `LINE_DEV_CA_CERT`

```text
Failed to setup app: error encountered during setup hook:
Не удалось прочитать LINE_DEV_CA_CERT: файл сертификата недоступен.
```

`tauri dev` переключает рабочий каталог в `src-tauri` (`set_current_dir(dirs.tauri)`
в CLI), поэтому относительный `.provider\tls.crt` раньше искался как
`src-tauri\.provider\tls.crt` — и не находился.

**Исправлено:** путь теперь ищется от текущего каталога, затем от `src-tauri`,
затем **от корня репозитория**. Команда из способа 1 работает как есть. Абсолютный
путь используется ровно как указан. В консоли печатается список проверенных
путей и тот, который сработал:

```text
[line] WARNING: dev-provider-ca active — trusting 1 extra root(s) from D:\Проекты\Line-Launcher\.provider\tls.crt
```

Если файл всё равно не найден — задайте абсолютный путь:

```powershell
$env:LINE_DEV_CA_CERT = "D:\Проекты\Line-Launcher\.provider\tls.crt"
```

Проверьте, что сертификат вообще создан: его делает `npm run provider:serve` при
первом запуске. Без запущенного провайдера лаунчер подключаться не к чему.

#### Способ 2: добавить сертификат в хранилище ОС

> **Осторожно.** Это делает сертификат доверенным **для всей машины и всех
> приложений**, а его закрытый ключ лежит рядом — `.provider/tls.key`. Любой, кто
> получит этот файл, сможет прозрачно подменять любой TLS-трафик на этой машине.
> Делайте так только на одноразовой тестовой машине и **обязательно удалите**
> сертификат после проверки. Способ 1 безопаснее.

**Windows (PowerShell от администратора):**

```powershell
Import-Certificate -FilePath .provider\tls.crt -CertStoreLocation Cert:\LocalMachine\Root
# удалить после тестов:
# Get-ChildItem Cert:\LocalMachine\Root | Where-Object { $_.Subject -eq "CN=localhost" } | Remove-Item
```

**macOS:**

```sh
sudo security add-trusted-cert -d -r trustRoot \
  -k /Library/Keychains/System.keychain .provider/tls.crt
```

**Linux (Debian/Ubuntu):**

```sh
sudo cp .provider/tls.crt /usr/local/share/ca-certificates/line-dev.crt
sudo update-ca-certificates
# удалить: sudo rm /usr/local/share/ca-certificates/line-dev.crt && sudo update-ca-certificates
```

После изменения хранилища **перезапустите лаунчер**.

#### Java-клиент

Java использует своё хранилище доверия, и способа 1 это не касается. Если demo-игра падает
на `PKIX path building failed`, импортируйте сертификат в JDK:

```sh
keytool -importcert -noprompt -alias line-dev -file .provider/tls.crt \
  -cacerts -storepass changeit
```

## 5. Реальный Minecraft и мод провайдера

Demo-пак проверяет транспорт, но не интеграцию с игрой. Что нужно сделать:

1. **Собрать реальную сборку** (Minecraft + ваш лоадер + мод авторизации) и
   положить внутрь `line-launch.json` по контракту из
   [PROVIDER.md](PROVIDER.md). Пути — только относительные, classpath — только
   `.jar` внутри архива, произвольные JVM-флаги запрещены. Пак должен быть полным
   (клиент, библиотеки, ассеты, нативы): лаунчер ничего не докачивает со сторонних
   зеркал, а право распространять сборку — на вас. Разбор команды запуска,
   каталогов и защиты файлов — [GAME.md](GAME.md).
2. **Встроить справочный клиент** `examples/mod-client/LineTicketClient.java` в мод
   и вызвать `LineTicketClient.request()` до подключения к серверу, затем
   `exchange(ticket)`. Ответ обмена — ваша игровая сессия/профиль.
3. **Реализовать серверную часть** по образцу `examples/provider/server.mjs`:
   ticket одноразовый, TTL ≤ 120 с, привязан к `server_id`, `sha256`, `channel_id`,
   `username`; повтор — 409, истечение — 401, несовпадение — 403.
4. **Проверить матрицу версий Java:** ваша сборка объявляет `java_major`; лаунчер
   ищет ровно эту версию (`JAVA_HOME`, `PATH`, стандартные каталоги). Убедитесь, что
   на тестовой машине стоит именно она, иначе получите ошибку `JAVA_REQUIRED`.

**Готово, если:** игрок входит в Minecraft под своим ником, сервер видит
корректную сессию, повторный запуск со старым ticket невозможен.

### 6.1. «После нажатия кнопки компьютер загрузился в BIOS»

Этот отчёт пришёл с продакшена, и первое, что нужно зафиксировать: **лаунчер не
может отправить машину в настройки прошивки.** Проверено по коду:

- ни одна команда не запускает `bcdedit`, `msconfig`, `reg`, `wmic`, `shutdown`
  или `powershell`; в `src-tauri/` нет ни одного вызова с повышением прав;
- `line::window`, `line::tray`, `line::minecraft` и `line::launch` работают
  только с окнами, иконкой в трее, файлами и процессом Java;
- кнопка «Запуск без сервера» (раньше — «Тестовый режим») меняет ровно одно:
  выбрасывает из командной строки `--quickPlay*`, `--server` и `--port`, чтобы
  Minecraft открылся в главном меню (`minecraft_core::remove_automatic_joins`).
  Никакого отношения к прошивке это не имеет.

Машина, которая после нагрузки встаёт в BIOS, — это **сброс, случившийся до
загрузки ОС**, поэтому Windows не успевает записать синий экран. Типичные причины
по убыванию вероятности:

| Причина                       | Как проверить                                                 |
| ----------------------------- | ------------------------------------------------------------- |
| Нестабильный профиль XMP/EXPO | Выключить XMP/EXPO в BIOS, погонять так неделю                |
| Просадка питания (БП)         | Заменить БП или проверить нагрузкой; сброс обычно под пиком   |
| Севшая батарейка CMOS         | Дата/время сбрасываются, настройки BIOS теряются              |
| Перегрев                      | Мониторинг температур CPU/GPU под нагрузкой                   |
| Сбитый порядок загрузки       | Проверить, что загрузочный диск первый и режим UEFI, а не CSM |

Что делает лаунчер, чтобы не гадать: TXT-экспорт в разделе «Логи и поддержка» в
настройках теперь дописывает к отчёту историю неожиданных перезагрузок из
журнала `System` (`Kernel-Power` 41, `BugCheck` 1001, `EventLog` 6008) —
**только чтение**, без прав администратора. Если есть события 41 и нет 1001,
это сброс ниже ОС, то есть питание/память/перегрев, а не ошибка приложения.
См. `src-tauri/src/line/hardware.rs`.

Отдельно про память: лаунчер больше не передаёт `-Xms` равным `-Xmx`. Пара
`-Xms8G -Xmx8G` заставляет JVM закоммитить всю кучу одним блоком на старте — на
машине с системным файлом подкачки это создаёт пик ровно в момент запуска игры,
а на разогнанной памяти такой пик и приводит к сбросу. Стартовая куча теперь
четверть максимума (512 МБ…2 ГБ) и дорастает по мере надобности. Подробности —
`docs/GAME.md`, раздел «Команда запуска».

## 7. Подпись кода и обновления

Сейчас release-workflow собирает **неподписанные** кандидаты и ничего не
публикует. Это осознанное решение: ключи должны быть у Plus In Plus.

### 7.1. Подпись

- **Windows:** сертификат Code Signing (OV/EV) в GitHub Secrets; настройте
  `bundle.windows.certificateThumbprint` / `signCommand` в Tauri-конфигурации.
  Без подписи SmartScreen будет предупреждать пользователей.
- **macOS:** Apple Developer ID Application, затем нотаризация:
  переменные `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_ID`,
  `APPLE_PASSWORD` (app-specific), `APPLE_TEAM_ID`. Без нотаризации Gatekeeper
  заблокирует приложение.
- **Linux:** подпись пакетов не обязательна; распространяйте `.deb`/`.rpm`/AppImage
  с контрольными суммами.

### 7.2. Updater

1. Сгенерируйте ключ **у себя**, приватная часть никогда не попадает в репозиторий:

   ```sh
   npm run tauri signer generate -- -w ~/.tauri/line-launcher.key
   ```

2. Публичный ключ впишите в `plugins.updater.pubkey`, приватный — в CI-секрет
   `TAURI_SIGNING_PRIVATE_KEY` (и `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`).
3. Поднимите endpoint обновлений и заполните `plugins.updater.endpoints`.
4. Включите `bundle.createUpdaterArtifacts: true`.
5. Добавьте отдельный job публикации, который выполняется только после успешных
   проверок разделов 2–5 и вручную подтверждается.

## 10. Что прислать, если что-то не работает

Минимальный набор для быстрой диагностики:

1. ОС и версия, версия Rust (`rustc --version`), Node (`node -v`), Java (`java -version`).
2. Полная команда и **первая** ошибка из вывода (не последняя).
3. Для сбоев запуска: лог провайдера (`.provider` сервер пишет причины отказа) и
   статус игры в интерфейсе.
4. Для сбоев установки: код ошибки из интерфейса (`INTEGRITY`, `UNSAFE_ARCHIVE`,
   `DISK_SPACE`, `BUSY`…) — он стабилен и достаточен для локализации проблемы.

Логи не должны содержать ticket, пароль или access-токен. Это больше не
соглашение: значение пишется через тип `Field`, который прогоняет текст через
`scrub`, а прочие конструкторы — только числа и флаги. Подробности,
расположение файлов и формат письма: [LOGGING.md](LOGGING.md).

Самый быстрый способ собрать отчёт — **Настройки → Логи и поддержка →
«Сохранить отчёт TXT»**: файл с путями, версией, провайдером, состоянием сессии
и полными логами за период хранения. Его можно прикрепить целиком. Там же есть
«Открыть папку с логами» для сырых файлов.
